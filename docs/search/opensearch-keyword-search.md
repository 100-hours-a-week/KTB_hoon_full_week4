# 키워드 검색 OpenSearch 전환

MySQL FULLTEXT 기반 키워드 검색이 매치가 많은 검색어에서 수십 초 걸리는 문제
(`fulltext-search-experiment.md`)를 OpenSearch 도입으로 해결했다. 2026-08-23 운영 반영.

| `?keyword=테니스&size=10` (운영 HTTP) | 실측 |
|---|---|
| 전환 직전 (MySQL FULLTEXT) | 42.44 / 34.83초 |
| 전환 직후 (OpenSearch) | 1.15(첫 요청) / 0.21 / 0.17초 |

warm 기준 약 170~200배.

## 배경

MySQL FULLTEXT 는 매치 집합을 통째로 만든 뒤에야 정렬을 시작하므로 `LIMIT 11` 이
전파되지 않고, MySQL 안에서 시도한 우회 일곱 가지가 전부 실패했다. OpenSearch(내부 엔진
루씬)에서는 같은 문제가 구조적으로 생기지 않는다.

| MySQL FULLTEXT 에서 막힌 것 | OpenSearch 에서는 |
|---|---|
| 매치 전량을 만든 뒤에야 정렬 → `LIMIT` 무력 | 인덱스 자체를 최신순으로 미리 정렬(index sorting). 최신순 요청은 위에서부터 걷다가 11건이 차면 멈춘다 |
| 정렬하려면 매치 전량의 정렬 키 확인 | 정렬값이 색인에 함께 저장(doc values)돼 행 조회가 필요 없다 |
| phrase 검증이 매치 건수에 초선형 | 토큰 위치 대조가 기본 동작이라 빠르다 |
| 커서 페이지네이션 | `search_after` 가 기존 `(createdAt, id)` 복합 커서와 같은 개념이라 그대로 이식된다 |
| 결과 0건 필터 조합이 100만 행 스캔 (별개 문제) | 필터도 역색인이라 교집합이 비면 즉시 0건. 검색 전체를 옮기면 함께 풀린다 |

이 대응은 구조 설명이고, 결론은 아래 측정으로 확인했다.

## 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 매칭 방식(analyzer) | MySQL 과 동일한 2글자 ngram + phrase 재현 | 결과가 같아야 성능 비교 검증이 성립한다. nori 는 별도 증분 |
| 적용 범위 | 키워드 검색만 | keyword 가 있을 때만 OpenSearch. 목록·필터는 MySQL 유지 — 변경과 장애 영향 최소화 |
| 클라이언트 | 의존성 추가 없이 스프링 내장 `RestClient` + Jackson | 필요한 호출이 검색·색인·삭제 세 개뿐. 전송하는 JSON 이 검증에 쓴 curl 과 동일하다는 장점. 벌크 등 필요 시 재검토 |
| 운영 배포 위치 | 기존 EC2(t3.small)에 공식 이미지 컨테이너로 추가 | 추가 비용 월 $1 미만(EBS 증설분). 별도 EC2(+$15)·관리형(+$30)과 비교해 결정. 코드가 `OPENSEARCH_URI` 하나에만 의존해 이전이 쉽다 |
| 관리형(AWS OpenSearch Service) | 보류 | 프리티어 소멸·크레딧 0 확인. 월 $30~35 실비 대비, 현 구조의 유일한 문제(유휴 후 첫 요청 지연)는 더 싼 수단(t3.medium/별도 t4g.small)으로 풀린다 |

## 색인 설계

- 2글자 ngram analyzer(`min_gram=2, max_gram=2`, `token_chars: [letter, digit]`) —
  MySQL `ngram_token_size=2` 재현
- index sorting `(created_at desc, id desc)` — 최신순 검색의 조기 종료를 만드는 핵심 설정
- 필드: `title`/`content`(text), 정렬 키 `created_at`/`id`, `deleted`/`blinded`,
  필터 컬럼 5개(`category`/`meeting_type`/`recruit_status`/`sido`/`sigungu`, keyword 타입)
- `created_at` 은 date 타입이라 밀리초 정밀도지만, `(created_at, id)` 동점 규칙과 데이터의
  단조성(날짜 범위 문서 7절) 덕에 정렬 순서는 MySQL 과 동일
- 색인 생성·적재 도구는 `bench/opensearch/`. 로컬 100만 건 적재 27.5초, 색인 222.8MB
  (MySQL `posts` 486MB 의 절반 이하)

## 로컬 검증 — 결과 동등성과 조기 종료

로컬 MySQL 에서는 원 문제가 재현되지 않았다.

| 키워드 | 매치 | 로컬 MySQL (3회) | 운영 RDS (참고) |
|---|---|---|---|
| `포핸드` | 3,478 | 0.10~0.13초 | 0.07~1.26초 |
| `복식` | 49,685 | 0.19~0.26초 | 22.97~30.50초 |
| `라켓` | 69,237 | 0.23~0.24초 | 32.61~41.94초 |
| `테니스` | 41,679 | 0.28~0.31초 | 33.19~51.80초 |
| 매치 0건 | 0 | 0.07~0.08초 | 즉시 |

측정은 운영과 같은 쿼리 형태(`SELECT p.* ... ORDER BY created_at DESC, id DESC LIMIT 11`),
`docker exec` 오버헤드(`SELECT 1` 기준 0.09~0.11초) 포함. 빠른 원인은 환경 차이다 —
로컬 버퍼풀 1.5GB 에 `posts` 486MB 가 전부 올라가는 반면 RDS 는 128MB. 다만 실행 계획은
로컬에서도 동일하게 FT 노드가 매치 전량(`rows=41679`)을 넘긴다. 같은 구조가 좋은 하드웨어로
빨리 끝날 뿐이다.

따라서 로컬 검증 기준을 절대 시간이 아니라 두 가지로 잡았다: 결과 동등성, 읽는 양.

결과 동등성 — 매치 건수(활성 필터 포함)가 다섯 시나리오 전부 MySQL 과 일치하고,
`포핸드`·`테니스` 의 상위 11건 id 도 완전히 같다. 2글자 ngram + phrase 재현이 의도대로
동작한다는 확인이다.

| 키워드 | MySQL Filter 통과 | OpenSearch `_count` | 상위 11건 id |
|---|---|---|---|
| `포핸드` | 3,308 | 3,308 | 일치 |
| `복식` | 47,409 | 47,409 | — |
| `라켓` | 66,117 | 66,117 | — |
| `테니스` | 39,795 | 39,795 | 일치 |
| 매치 0건 | 0 | 0 | — |

읽는 양 — `profile` 기준 `테니스` 검색에서 phrase 쿼리가 순회한 문서는 35건이다.
같은 11건을 뽑는 데 MySQL FULLTEXT 는 41,679건을 읽었다. index sorting 이 만든 조기 종료다.

```
PhraseQuery: next_doc_count=35     ← 매치 39,795건 중 35건에서 멈춤
collector: search_top_hits 0.10ms
```

시간 — `took` 이 전 키워드 1~9ms 로 매치 건수와 무관하다. 전체 건수 집계를 강제해도
(`track_total_hits=true`) 1~2ms.

| 키워드 | 매치 | took (5회) |
|---|---|---|
| `포핸드` | 3,308 | 2~8ms |
| `복식` | 47,409 | 1~8ms |
| `라켓` | 66,117 | 1~4ms |
| `테니스` | 39,795 | 1~9ms |
| 매치 0건 | 0 | 1ms |

절대값은 로컬 참고치다. 매치 건수 무관성과 "35건만 읽는다"는 구조의 증거라 환경과 무관하게
유지된다 — MySQL 의 `rows=매치 전량` 이 환경과 무관했던 것과 같은 이유다.

## 애플리케이션 연동

| 파일 | 역할 |
|---|---|
| `api/repository/search/PostSearchIndex.java` | 색인 포트. `searchIds` / `index` / `delete` / `isEnabled` |
| `.../search/opensearch/OpenSearchPostSearchIndex.java` | `RestClient` 기반 구현 |
| `.../search/DisabledPostSearchIndex.java` | 비활성 시 구현 |
| `OpenSearchProperties` + `global/config/OpenSearchConfig` | `opensearch.enabled` 값으로 구현 선택 |
| `.../search/jpa/JpaSearchRepositoryAdapter.java` | 키워드 경로 라우팅 |
| `.../search/jpa/JpaSearchRepository.java` | id 목록 하이드레이션 쿼리 추가 |

검색 흐름: 키워드가 있으면 OpenSearch 에서 최신순 id 11개만 받고, 본문·작성자는 MySQL 에서
`JOIN FETCH member` 로 채워 색인이 준 순서로 재정렬한다. 색인에 본문·닉네임을 넣지 않는
이유는 화면 데이터의 원본을 MySQL 하나로 유지해 동기화 범위를 최소화하기 위해서다.
커서는 기존 복합 커서가 `search_after` 로 그대로 이어진다.

전환 스위치는 설정값(`opensearch.enabled`)이다. local 은 on, prod 는 환경변수, test·inmemory
는 기본 off. OpenSearch 호출이 실패하면 경고 로그 후 기존 FULLTEXT 쿼리로 폴백한다 —
검색이 실패하는 대신 느려지는 쪽을 택했다.

색인 동기화는 글이 바뀌는 6곳(생성·발행·수정·마감·삭제·블라인드)에서 수행한다.
초기 구현은 저장 직후 직접 호출이었고, 이후 트랜잭셔널 아웃박스로 교체했다
(`search-index-outbox.md`).

로컬 E2E: 검색 0.021초(강제 폴백 경로 0.349초), 생성 → 노출 → 삭제 → 제거 동기화,
커서 2페이지 중복 없음, OpenSearch 중지 시 폴백 동작을 확인했다.

## 운영 측정

운영 환경: 기존 EC2(t3.small, 2GB)에 공식 이미지 컨테이너로 추가(힙 512m), 스왑 2GB 와
EBS 16GB 증설 선행. RDS 100만 건 초기 적재 140.4초, 색인 310MB. 전환 직전과 직후를
같은 날, 같은 축(HTTP)으로 측정했다.

| 요청 | 직전 (FULLTEXT) | 직후 (OpenSearch, 3회) |
|---|---|---|
| `테니스` (매치 4.2만) | 42.44 / 34.83초 | 1.148 / 0.209 / 0.172초 |
| `복식` (5.0만) | 역대 22.97~30.50초 | 0.253 / 0.170 / 0.162초 |
| `라켓` (6.9만) | 역대 32.61~41.94초 | 0.164 / 0.146 / 0.169초 |
| `포핸드` (0.3만) | 1.53초 | 0.185 / 0.129 / 0.151초 |
| 매치 0건 | 0.128초 | 0.096 / 0.086 / 0.082초 |
| 조건 없음 (대조, MySQL 경로) | 0.165초 | 0.312 / 0.086 / 0.080초 |

- 매치 수만 건 키워드가 전부 0.2초 안쪽으로 내려왔고, 매치 건수와 응답 시간의 상관이
  사라졌다
- 폴백 경고 로그 0건 — 전 요청이 OpenSearch 경로
- 키워드 없는 목록은 변화 없음 — MySQL 경로 그대로라는 대조 확인

동기화도 확인했다. 생성 → 검색 노출, 삭제 → 검색 제외·색인 문서 제거. 색인 반영은
refresh 주기(1초) 뒤에 검색에 노출되는 near-realtime 구조다(생성 직후 검색은 비고
2초 뒤 조회로 확인. 이후 아웃박스 전환으로 최대 ~2초).

유휴 후 첫 요청만 느린 현상이 있다. 필터를 붙인 검색이 느리다는 제보를 조합별로 측정한
결과 서버 응답은 0.10~0.35초로 필터와 무관했고, 실체는 첫 요청만 0.3~1.1초인 패턴이었다
(브라우저 개발자도구로도 확인). 원인은 2GB 인스턴스에서 유휴 시간 동안 커널이 프로세스
페이지를 스왑으로 내리는 것으로, 근본 해법은 메모리 증설이며 t3.small 을 유지하는 동안
감수하기로 했다.

## 남은 것 / 하지 않은 것

- 결과 0건 필터 조합의 100만 행 스캔(8.7초)은 남아 있다. 적용 범위를 키워드 검색으로
  한정했기 때문으로, 검색 전체를 OpenSearch 로 옮기면 함께 풀린다
  (`date-range-search-troubleshooting.md` 12절)
- DB-색인 정합성은 트랜잭셔널 아웃박스로 해소했다(`search-index-outbox.md`). 대량 어긋남의
  최후 수단으로 `03_initial_load_ec2.sh` 재적재(멱등)가 있다
- 검색 품질은 별도 증분이다. 현재는 부분 문자열 매칭이라(운영 확인: `테니`·`니스` 는 잡히고
  `테니쓰`·`태니스` 같은 오타는 0건) 개선 순서는 ngram+nori 멀티필드 → fuzziness →
  (커서와의 충돌 설계 후) 관련도 정렬
- 벡터 검색(k-NN)은 쓰지 않는다. 기능은 기본 포함이지만 ① 저장·검색마다 임베딩 모델이
  필요하고(비용 또는 메모리) ② 100만 건 × 수백 차원 + HNSW 는 수 GB 급으로 색인 310MB 와
  체급이 다르며 ③ 유사도 점수 정렬이 커서의 정렬 키 불변 전제를 깨고 ④ 키워드 검색이라는
  용도에는 lexical + nori·fuzziness 로 충분하다. 자연어 질의·추천이 생기면 하이브리드로
  재검토한다
