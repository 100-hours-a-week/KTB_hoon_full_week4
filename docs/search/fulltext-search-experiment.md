# 키워드 검색이 느린 문제 — 실험 기록

운영에서 키워드("테니스") 검색이 34초 걸리는 걸 발견하고 원인을 좁혀간 기록이다.

## 결론

**11건만 필요한데 FULLTEXT 가 매치 전량을 넘겨준다. `LIMIT` 이 통하지 않는다.**

운영과 같은 쿼리(`SELECT p.* ... ORDER BY created_at DESC, id DESC LIMIT 11`)를
검색어별로 나눠 `EXPLAIN ANALYZE` 로 잡았다.

| 키워드 | 매치 | FT 노드가 넘긴 행 | 반환 | 실측 |
|---|---|---|---|---|
| `포핸드` | 3,478 | 3,478 | 11 | 0.07 ~ 1.26초 |
| `복식` | 49,685 | 49,685 | 11 | 22.97 ~ 30.50초 |
| `라켓` | 69,237 | 69,237 | 11 | 32.61 ~ 41.94초 |
| `테니스` | 41,679 | 41,679 | 11 | 33.19 ~ 51.80초 |
| 매치 0건 | 0 | 0 | 0 | 0.00초 |

```
-> Limit: 11 row(s)                                    ← 11건만 달라고 했는데
  -> Sort row IDs: created_at DESC, id DESC
    -> Filter: ... MATCH(...)              (rows=47409)
      -> Full-text index search on p ...   (rows=49685) ← 4.9만 건이 올라온다
```

`Limit: 11` 이 계획 맨 위에 있는데도 아래로 전파되지 않는다. 다섯 시나리오 전부 그렇다.

다른 의심들은 같은 축의 측정으로 배제했다.

| 의심 | 배제 근거 |
|---|---|
| FULLTEXT 자체가 느린 것 아닌가 | 매치 0건은 `rows=0` 으로 즉시 끝난다 |
| 11행을 읽어오는 비용 아닌가 | `SELECT id` 로 바꿔도 33~35초로 같다 |
| 인덱스를 잘못 고른 것 아닌가 | 다른 인덱스를 강제하면 `ERROR 1191` — 문법 차원에서 거부 |
| 조건을 좁히면 되지 않나 | `category` 필터를 붙여도 FT `rows` 는 41,679 그대로, 34.20초 |
| 테이블이 커서 아닌가 | 같은 테이블을 날짜 조건으로 뽑으면 인덱스가 11행만 읽고 끝난다 |

남는 변수는 매치 건수 하나다. 수천 건이면 1초 남짓, 수만 건이면 수십 초, 0건이면 즉시 끝난다.

MySQL 안에서 우회를 일곱 가지 시도해 전부 막혔다(뒤의 「종합」 표). 최신순 정렬을 통째로
버려도 `테니스` 는 16~23초에서 멈춘다. `LIKE` 로 되돌리는 것도 답이 아니다 — 매치가 없을 때
94만 행을 훑어 13.13초로, 최악 케이스가 정반대로 옮겨갈 뿐이다.

측정하다 여러 번 틀렸고 그때마다 결론이 바뀌었다. 부록에 남겼다.

## 측정 방법과 환경

시간은 mysql 클라이언트가 찍는 실제 소요 시간(`N rows in set (X sec)`)으로 재고,
`EXPLAIN ANALYZE` 는 `rows` 와 실행 계획을 읽는 용도로만 쓴다. FULLTEXT 쿼리에서는
노드 시간이 실제와 크게 어긋나는 경우가 있어서다(부록 A1). 실행 간 편차가 커서
가능한 한 반복해서 재고 범위로 적는다(부록 A2).

| 항목 | 내용 |
|---|---|
| 대상 | 운영 (EC2 nginx → backend → AWS RDS MySQL 8) |
| 데이터 | `bench/sql` 로 만든 모집글 100만 건 규모 (활성 940,445) |
| 인덱스 | `ft_posts_title_content (title, content) WITH PARSER ngram`, `ngram_token_size=2` |
| 페이지 | `size=10` → `LIMIT 11` |
| 버퍼풀 | 128MB (`innodb_buffer_pool_size`) |
| `posts` 크기 | 486MB (데이터+인덱스, FT 보조 테이블 제외) |

절대 시간은 이 환경의 값이다. 버퍼풀이 128MB 로 운영치고 작고 `posts` 가 그 3.8배라,
사양이 다르면 숫자도 달라질 수 있다. 다만 같은 환경 안에서의 상대 비교(`포핸드` 0.07초 vs
`테니스` 34.17초)와, FT 노드가 매치 전량을 받는다는 것, 우회가 막힌 것은 환경과 무관하다.

## 문제 발견

| 요청 | 응답 시간 |
|---|---|
| `?keyword=테니스&size=10` (첫 요청) | 41.38초 |
| `?keyword=테니스&size=10` (반복 3회) | 34.92 / 34.00 / 34.52초 |
| 조건 없음 (대조) | 0.090 / 0.117 / 0.112초 |

키워드가 붙은 요청만 느렸다. 코드를 보면 `keyword` 유무로 쿼리가 갈린다 — 있으면 FULLTEXT
네이티브 쿼리, 없으면 JPQL. 범위가 여기로 좁혀졌다.

## 실험 1 — 요청 파라미터로 줄일 수 있나

가장 싼 것부터 확인했다.

| 물어본 것 | 어떻게 | 결과 |
|---|---|---|
| 10건 뽑느라 느린가 | `size=1` 로 축소 | 33.5초 (변화 없음) |
| 조건이 넓어서인가 | `category` 필터 추가 | 33.5초 (변화 없음) |

둘 다 배제. 비용이 반환 건수나 조건 개수와 무관하다. HTTP 로는 더 못 좁혀서 SQL 로 내려갔다.

## 실험 2 — 매치 규모 확인

```sql
SELECT COUNT(*) FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE);
```

41,679건. 활성 940,445건 대비 약 4.4%. 11건 반환하려고 4만 건짜리 집합을 다루고 있었다.

## 실험 3 — `ORDER BY` 없이 `LIMIT` 만 남겨보기

```sql
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
LIMIT 11;
```

실제 소요 15.5~16.4초(연속 2회). 다른 날 같은 쿼리가 23.27초까지 나와서(실험 6),
이 문서는 `테니스` 의 정렬 없는 값을 16~23초 범위로 다룬다.

`ORDER BY` 도 행 페치도 없는데 이만큼 걸린다. InnoDB FULLTEXT 는 매치 집합을 먼저
통째로 만들고 나서 행을 흘려보내는 구조라, `LIMIT` 이 11이든 1이든 앞단 비용이 그대로다.
필요한 만큼 찾으면 멈추는 조기 종료가 없다.

## 실험 4 — `ORDER BY` 를 붙이면

| | 실제 소요 (이 회차) |
|---|---|
| `LIMIT 11` | 15.5~16.4초 |
| `ORDER BY id DESC LIMIT 11` | 36.15초 |

약 1.6~2.3배 차이다. `EXPLAIN ANALYZE` 의 `rows` 를 보면 `ORDER BY` 가 없을 때 FT 노드가
`rows=11`, 있을 때 `rows=41679` 다. 정렬하려면 매치 전량의 정렬 키를 확인해야 한다.
정렬 연산 자체는 싸다(`Sort` 노드 92ms) — 비싼 건 정렬하려고 전량을 확인하는 쪽이다.

## 실험 5 — 우회로가 있나

| 시도 | 결과 |
|---|---|
| 커서로 `id` 범위 제한 (`AND id > 990000`) | FT 노드 `rows=41679` 그대로. 조건은 뒤에서 420건으로 걸러짐 |
| 날짜 범위 결합 | FT `rows=41679` → 날짜 통과 475건. 오히려 악화 |
| `FORCE INDEX` 로 다른 인덱스 강제 | `ERROR 1191 Can't find FULLTEXT index matching the column list` |

`MATCH` 를 WHERE 에 쓰면 FULLTEXT 인덱스가 접근 경로여야만 한다. "날짜로 먼저 좁히고
키워드는 행마다 검사" 라는 방식은 MySQL 에서 표현 자체가 안 된다.

## 실험 6 — 무엇이 비용을 정하나: 대조군

먼저 배경 하나. `ngram_token_size=2` 라 색인은 2글자 단위로 잘린다. `테니스` 는
`[테니][니스]` 2토큰이고, `라켓` 같은 2글자 검색어는 토큰이 하나다. 검색어를 따옴표로
감싼 phrase 검색은 토큰이 2개 이상일 때만 "토큰들이 붙어 있는지" 위치 대조가 필요하다.

`bench/sql/03_words.sql` 이 주제별 단어에 가중치를 부여하므로, 테니스 주제(topic 21) 안에서
주제·문체를 고정하고 변수만 바꾼 대조군을 만들 수 있었다. 측정은 전부
`SELECT id ... LIMIT 11` 의 2회차 실제 소요 시간이고, 변수를 하나만 두려고 `ORDER BY` 는
뺐다 — 이 선택의 대가는 실험 8에서 드러난다.

| 키워드 | 토큰 | 매치 | 시간 |
|---|---|---|---|
| `포핸드` | `[포핸][핸드]` 2개 | 3,478 | 0.13초 |
| `라켓` | `[라켓]` 1개 | 69,237 | 0.20초 |
| `타이브레이크` | `[타이][이브][브레][레이][이크]` 5개 | 99 | 0.26초 |
| `복식` | `[복식]` 1개 | 49,685 | 0.32초 |
| `테니스` | `[테니][니스]` 2개 | 41,679 | 23.27초 |

매치 건수만으로는 설명이 안 된다 — 매치가 가장 많은 `라켓`(69,237건)이 가장 빠르다.
토큰 수만으로도 안 된다 — `포핸드` 와 `테니스` 는 똑같이 2토큰인데 0.13초와 23초다.
둘이 같이 작용한다. 1토큰이면 phrase 검증이 없어 목록만 읽으면 끝이라 매치 건수와 사실상
무관하고(49,685건 0.32초 / 69,237건 0.20초), 2토큰부터는 목록을 교차시키고 글자 위치가
인접한지 대조해야 해서 매치 건수에 초선형으로 비싸진다(12배 매치에 179배 시간).

단, 이 표는 전부 `ORDER BY` 없는 조건에서의 값이다. "1토큰이면 매치가 많아도 싸다" 는
실험 8에서 뒤집힌다.

`ngram_token_size` 를 1로 낮추면 1글자 검색이 가능해지는 대신 모든 다글자 검색어가
다토큰이 된다(`복식` → `[복][식]`, `테니스` → `[테][니][스]`). 이건 측정하지 않기로 했다.
토큰이 늘면 비싸진다는 방향은 확인됐으니 어느 값이 나와도 판단이 안 바뀌는데,
`ngram_token_size` 는 재시작이 필요한 파라미터라 100만 건 FT 인덱스 재구축을 적용·복원
두 번 치러야 한다. 애초에 성능 개선안이 아니라 1글자 검색이라는 기능 요구에서 나온
이야기이므로, 그 기능이 필요해질 때 재는 게 맞다.

## 실험 7 — `LIKE` 와 비교

| 키워드 | LIKE | FULLTEXT |
|---|---|---|
| `테니스` (매치 41,679) | 0.02초 / 339행 | 16~23초 |
| `리그오브레전드` (매치 0) | 13.13초 / 전량 | 0.01초 |

같은 키워드에서 800~1,150배 차이다. `LIKE` 는 인덱스가 주는 순서를 그대로 걷다가 339행에서
조기 종료하고, 반대로 매치가 없으면 94만 행을 다 훑는다. 두 방식의 최악 케이스가 정반대라 —
`LIKE` 는 매치가 없을 때, FULLTEXT 는 매치가 많을 때 무너진다 — 한쪽으로 되돌리는 건
문제를 옮기는 것이다.

참고로 `LIKE` 는 `EXPLAIN ANALYZE`(33.5ms)와 실제 소요(0.02초)가 거의 일치했다.
B-tree 스캔에는 FULLTEXT 같은 준비 단계가 없어서다.

## 실험 8 — 실제 API 형태(`ORDER BY` 포함)로 다시 재기

실험 6은 전부 `ORDER BY` 없는 측정이었는데, 실제 API 는 최신순 정렬을 한다.
1토큰 검색어에 정렬만 붙여 다시 쟀다.

```sql
SELECT id FROM posts
WHERE MATCH(title,content) AGAINST('"복식"' IN BOOLEAN MODE)
ORDER BY created_at DESC, id DESC LIMIT 11;
```

| 키워드 | 토큰 | 매치 | `ORDER BY` 없이 (2회차) | `ORDER BY` 붙여서 (1회차) |
|---|---|---|---|---|
| `복식` | 1 | 49,685 | 0.32초 | 30.50초 (2회차 28.48초) |
| `라켓` | 1 | 69,237 | 0.20초 | 34.86초 |

"1토큰이면 싸다" 는 정렬이 없을 때만이다. phrase 검증이 아예 일어나지 않는 검색어도
정렬이 붙으면 수십 초가 된다. 매치 집합은 실험 6의 그 쿼리들과 완전히 같다 —
정렬하려면 매치 전량의 정렬 키를 확인해야 하기 때문이다.

### 두 비용이 더해지는지는 가릴 수 없었다

phrase 검증 비용과 정렬 비용이 더해지는 구조인지 확인하려고 `테니스` 를 운영과 같은
정렬 절로 다시 쟀다(앞의 36.15초는 `ORDER BY id DESC` 였다).

```sql
SELECT id FROM posts
WHERE MATCH(title,content) AGAINST('"테니스"' IN BOOLEAN MODE)
ORDER BY created_at DESC, id DESC LIMIT 11;
```

38.72초. 위 표에서 매치당 정렬 비용을 뽑으면 0.5~0.6ms 인데(`복식` 30.50초/49,685건,
`라켓` 34.86초/69,237건), 그 기준으로 `테니스` 의 정렬 몫은 21~25초다. 문제는 `테니스` 의
정렬 없는 기준값이 회차에 따라 15.5~16.4초(실험 3), 23.27초, 1회차로는 31.46초(실험 6)로
흔들린다는 것 — 16초 갈래를 쓰면 덧셈 예측이 36~41초로 실측과 맞고, 23~31초 갈래를 쓰면
44~56초로 안 맞는다. 덧셈이냐 배수냐는 결론을 못 냈고, 실험 10의 편차를 보고 나서는
이 층위의 논의 자체를 접었다.

### 어느 모델이든 바뀌지 않는 것

정렬 절을 통일해 나란히 놓으면 이렇다.

| 키워드 | 토큰 | 매치 | 총 시간 |
|---|---|---|---|
| `복식` | 1 | 49,685 | 30.50초 |
| `라켓` | 1 | 69,237 | 34.86초 |
| `테니스` | 2 | 41,679 | 38.72초 |

`테니스` 는 매치가 가장 적은데 가장 느리다. 토큰이 늘면 비싸진다 — 확정할 수 있는 건
이 방향뿐이고, 크기는 아니다.

의사결정에 필요한 부분은 여기다. **매치가 4만~7만이면 토큰 수와 무관하게 수십 초다.**
실험 6에서 괜찮아 보였던 `라켓`·`복식` 이 운영 형태에서는 `테니스` 와 같은 등급이었다.
안전한 건 `포핸드` 처럼 매치 자체가 적은 검색어뿐인데, 그건 사용자가 무엇을 치느냐에 달렸다.

매치 0건 대조도 확인했다. `리그오브레전드` 는 0.03초 / 0.01초 — 매치가 없으면 정렬할
것도 없으니, 정렬 비용이 매치 건수에 붙는다는 것과 어긋나지 않는다.

## 실험 9 — 복합 커서 배포 후 HTTP 재측정

날짜 범위 검색을 고치면서 네이티브 쿼리의 `ORDER BY` 도 `created_at DESC, id DESC` 로
바뀌었다. 키워드 검색에 영향이 있었는지 처음 발견했을 때와 같은 방식(HTTP)으로 다시 쟀다.

| 요청 | 배포 전 | 배포 후 |
|---|---|---|
| 조건 없음 (대조) | 0.090 / 0.117 / 0.112초 | 0.362 / 0.159 / 0.130초 |
| `keyword=포핸드` (매치 3,478) | — | 0.271 / 0.215 / 0.274초 |
| `keyword=테니스` (매치 41,679) | 34.92 / 34.00 / 34.52초 | 36.20초 (1회차만) |

달라진 게 없다. 복합 커서는 날짜 범위 검색을 고친 변경이고, 키워드 검색은 `ORDER BY` 절이
바뀌었을 뿐 매치 전량을 받아야 한다는 구조가 그대로다. 처음 발견 때의 30초대가 지금도
그대로라는 확인이다.

`포핸드` 는 HTTP 가 0.27초인데 같은 조건의 SQL 이 1.26초였다. HTTP 측정이 SQL 을 여러 번
돌린 뒤였다는 차이가 있어 두 값을 나란히 놓을 수는 없다. 회차를 맞춰 다시 재지는 않았다.

## 실험 10 — 시나리오별 실행 계획 (`EXPLAIN ANALYZE`)

앞의 측정은 대부분 `SELECT id` 였다. 여기서는 운영 쿼리와 완전히 같은 형태로 다시 잡았다.

```sql
SELECT p.* FROM posts p
WHERE MATCH(p.title, p.content) AGAINST('"키워드"' IN BOOLEAN MODE)
  AND p.deleted = false AND p.blinded = false
ORDER BY p.created_at DESC, p.id DESC LIMIT 11;
```

| 시나리오 | 토큰 | 매치 | FT 노드 `rows` | Filter 통과 | 반환 | 실측 |
|---|---|---|---|---|---|---|
| `포핸드` | 2 | 3,478 | 3,478 | 3,308 | 11 | 0.07초 |
| `복식` | 1 | 49,685 | 49,685 | 47,409 | 11 | 22.97초 |
| `라켓` | 1 | 69,237 | 69,237 | 66,117 | 11 | 32.61초 |
| `테니스` | 2 | 41,679 | 41,679 | 39,795 | 11 | 34.17초 |
| 매치 0건 | — | 0 | 0 | 0 | 0 | 0.00초 |

다섯 시나리오 전부 FT 노드의 `rows` 가 매치 건수와 정확히 같다.

```
-> Limit: 11 row(s)  (actual time=23644..23645 rows=11)          ← 11건만 필요한데
  -> Sort row IDs: created_at DESC, id DESC  (rows=11)
    -> Filter: blinded/deleted/MATCH  (rows=47409)
      -> Full-text index search on p using ft_posts_title_content  (rows=49685)   ← 4.9만 건을 받는다
```

`LIMIT` 이 안 듣는다는 걸 시간이 아니라 계획으로 보여주는 게 이 표다. 매치 0건은 `rows=0`
에 0.0147ms 로 끝나므로, 느린 원인이 FULLTEXT 자체가 아니라 매치 건수라는 것도 같은
축에서 확인된다.

### 행 페치는 비용이 아니다

같은 `테니스` 를 두 형태로 반복해서 쟀다.

| 형태 | 실측 |
|---|---|
| `SELECT p.*` (운영) | 35.40 / 34.17초 |
| `SELECT p.id` | 51.80 / 34.01 / 35.06 / 33.19초 |

구분이 안 된다. "34초의 범인은 행 페치" 라는 초기 가설이 운영 형태에서도 기각된다.
6회 중 5회가 33~35초에 모이므로 `테니스` 의 안정값은 34초 근방이고, 51.80초는 튄 값이다.

### 실행 간 편차가 크다

같은 쿼리를 다른 날 재면 값이 꽤 움직인다.

| 키워드 | 실측 범위 |
|---|---|
| `포핸드` | 0.07 ~ 1.26초 |
| `복식` | 22.97 ~ 30.50초 |
| `라켓` | 32.61 ~ 41.94초 |
| `테니스` | 33.19 ~ 51.80초 |

`복식` 이 22.97~30.50초로 흔들리는데, 실험 8에서 뽑았던 매치당 0.61ms vs 0.50ms 같은
차이는 이 폭 안에 들어간다. 매치당 비용을 상수로 다루거나 토큰 배수를 숫자로 못 박는 건
이 편차 위에서는 무의미하다. 검색어별로 말할 수 있는 건 자릿수까지다 — 매치가 수만 건이면
수십 초, 수천 건이면 1초 남짓, 0건이면 즉시.

## 실험 11 — 필터를 붙이면 / 키워드를 빼면

실험 10은 키워드만 바꿨다. 여기서는 조건을 더하거나 빼면 어떻게 되는지 봤다.

### 필터를 붙여도 FULLTEXT 는 전량을 받는다

```sql
SELECT p.* FROM posts p
WHERE MATCH(p.title, p.content) AGAINST('"테니스"' IN BOOLEAN MODE)
  AND p.category = 'EXERCISE'
  AND p.deleted = false AND p.blinded = false
ORDER BY p.created_at DESC, p.id DESC LIMIT 11;
```

```
-> Limit: 11 row(s)  (actual time=21537..21541 rows=11)
  -> Sort row IDs  (rows=11)
    -> Filter: ... (p.category = <cache>((@cat))) and MATCH(...)  (rows=11306)
      -> Full-text index search on p using ft_posts_title_content  (rows=41679)
```

카테고리는 세션 변수(`@cat` = `EXERCISE`)로 넘겼다. 계획의 `<cache>((@cat))` 이 그것이다.

| | FT 노드 `rows` | Filter 통과 | 반환 | 실측 |
|---|---|---|---|---|
| `테니스` (실험 10) | 41,679 | 39,795 | 11 | 34.17초 |
| `테니스` + `category` | 41,679 | 11,306 | 11 | 34.20초 |

필터는 FULLTEXT 뒤에서만 걸린다. 4만 건을 다 받은 뒤 1.1만 건으로 줄이므로 앞단 비용이
그대로고, 시간도 그대로다. 조건을 좁혀서 해결되는 문제가 아니다.

### 대조군 — 키워드 대신 날짜로 뽑으면 11행

같은 테이블에서 같은 11건을 뽑는데, 조건을 날짜로 주면 이렇게 된다.

```sql
SELECT p.* FROM posts p
JOIN members m ON m.id = p.member_id
WHERE p.created_at >= '2024-04-14 16:28:29' AND p.created_at < '2024-04-15 16:28:29'
  AND p.deleted = false AND p.blinded = false
ORDER BY p.created_at DESC, p.id DESC LIMIT 11;
```

```
-> Limit: 11 row(s)  (actual time=5.18..11.8 rows=11)
  -> Nested loop inner join  (rows=11)
    -> Index range scan on p using idx_posts_created_at_deleted_blinded (reverse),
       with index condition: ...  (actual time=1.59..2.36 rows=11 loops=1)
    -> Single-row covering index lookup on m using PRIMARY  (loops=11)
```

| 11건을 뽑는 조건 | 접근 경로 | 읽은 행 | 실측 |
|---|---|---|---|
| 날짜 범위 | `idx_posts_created_at_deleted_blinded` 역순 | 11 | 0.00초 |
| 키워드 `테니스` | `ft_posts_title_content` | 41,679 | 34.17초 |

같은 테이블, 같은 11건인데 읽는 양이 3,800배 차이난다. B-tree 인덱스는 필요한 만큼만 걷고
멈추는데 FULLTEXT 는 그게 안 된다. 조건이 달라서(날짜 vs 키워드) 엄밀한 1:1 대조는
아니지만, "MySQL 이 원래 11건을 어떻게 뽑는지" 와 "FULLTEXT 를 쓰면 어떻게 되는지" 를
같은 테이블에서 나란히 보여준다.

### 못 잰 것

`키워드 + 날짜 + 깊은 커서`(S7)와 그 대조군(S8b)은 커서 변수가 NULL 이라 무효였다.
1일 창에 382건뿐인데 `OFFSET 5000` 으로 커서를 뽑으려 해서 값이 안 잡혔다.

이 실패가 07 회차의 실패 원인도 밝혀줬다. 그때도 같은 `Zero rows (no matching row in
const table)` 이 나왔는데, 이건 NULL 비교를 옵티마이저가 상수 거짓으로 접을 때의 메시지다.
"날짜 범위에 데이터가 없어서" 라고 봤던 건 틀렸다 — 데이터는 2021-01-01 ~ 2026-08-09 로
5년 반에 걸쳐 있다(`SELECT MIN(created_at), MAX(created_at) FROM posts`).

## 남은 선택지

전부 뭔가를 포기해야 한다.

| 안 | 포기하는 것 | 근거가 되는 측정 |
|---|---|---|
| A. `ORDER BY` 를 버린다 | 최신순 정렬 | 부분적. 1토큰은 30초→0.32초, 2토큰은 39초→16~23초에서 멈춤 |
| B. LIKE 로 되돌린다 | FULLTEXT | 흔한 키워드 0.02초, 없는 키워드 13.13초 |
| C. 검색엔진을 도입한다 | MySQL 단일 스택 | 이후 착수 — `opensearch-keyword-search.md` (로컬 검증 완료, 운영 미반영) |

A 는 절반만 듣는다. 1토큰 검색어에는 30초를 0.32초로 만드는 카드지만 `테니스` 류가
16~23초로 남으므로, 최신순을 통째로 버리고도 최악 케이스가 안 풀린다. B 는 최악 케이스가
반대로 옮겨갈 뿐인데, 결과가 없는 검색(오타·없는 단어)은 실사용에서 흔하므로 되돌리면
더 자주 터지는 쪽을 고르게 된다. 그래서 C 로 갔다 — 그 뒤의 기록은
`opensearch-keyword-search.md` 에 있다.

## 데이터셋의 성격

측정 대상은 `bench/sql` 이 만든 합성 데이터다. 본문 단어를 `03_words.sql` 의 가중치 풀에서
뽑아 조립하므로 키워드별 매치 건수가 그 생성 규칙으로 결정된다. 지배 변수인 매치 건수가
곧 데이터의 성질이라, 실제 서비스에서 어떤 검색어가 몇 건에 매치될지는 이 문서로 알 수 없다.
100만 건에서 4.4~7.4% 매치가 나온 것이 합성 데이터의 산물인지 흔한 일인지도 별개 문제다.

옮겨갈 수 있는 결론은 조건부 형태다 — 매치 건수가 커지면 무너지고, MySQL 안에 막을
수단이 없다.

## 부록 — 측정하다 틀린 것들

결론을 이해하는 데는 필요 없지만, 같은 실수를 반복하지 않으려고 남긴다.

### A1. FULLTEXT 쿼리에서 `EXPLAIN ANALYZE` 의 노드 시간은 못 믿는다

```
-> Full-text index search on posts ...  (actual time=103..108 rows=11)   ← 108ms 라고 보고
...
1 row in set (25.29 sec)                                                 ← 실제로는 25.29초
```

`EXPLAIN ANALYZE` 는 반복자(iterator)가 도는 시간을 잰다. InnoDB FULLTEXT 는 반복자가
돌기 전에 엔진 내부에서 매치 집합을 만드는데, 그 준비 시간이 노드에 안 잡히는 경우가 있다.

| 키워드 | 토큰 | FT `rows` | 노드 시간 | 문장 실측 | |
|---|---|---|---|---|---|
| `복식` | 1 | 49,685 | 23,644ms | 23.82초 | 일치 |
| `라켓` | 1 | 69,237 | 33,488ms | 35.40초 | 5% 차이 |
| `테니스` | 2 | 41,679 | 20,722ms | 34.09초 | 1.6배 어긋남 |
| (초기) `테니스` | 2 | 11 | 108ms | 25.29초 | 234배 어긋남 |

1토큰은 둘 다 맞고 2토큰은 둘 다 어긋난다 — 토큰 수 축이 네 점 전부와 일관되지만,
계열당 두 점씩뿐이라 단정하지는 않는다. 확실한 건 `rows` 는 언제나 맞고 시간은 조건에 따라
과소보고된다는 것이라, `rows` 만 쓰고 시간은 따로 잰다. 준비 단계가 없는 B-tree 스캔
(`LIKE`)에서는 노드 시간과 실측이 거의 일치했다.

### A2. 한 번씩만 재면 못 믿는다

`포핸드` 가 1회차 4.45초, 2회차 0.13초로 34배 차이났다. 처음엔 캐시 회차 문제로 봤는데,
반복해서 재보니 회차와 무관하게 실행마다 흔들린다(`복식` 22.97~30.50초 /
`테니스` 33.19~51.80초). 그래서 이 문서는 범위로 적는다.

### A3. 버퍼풀 가설은 접었다

`테니스` 가 2회차에도 23초인 걸 보고 버퍼풀(128MB)에 작업 집합이 안 들어가서라고 봤었다.
같은 쿼리가 다른 시점엔 16초로도 나와서 접었다 — 메모리에 안 들어가 묶이는 거라면 값이
그렇게 움직이지 않는다. 영향이 없다는 뜻은 아니고, 히트율을 재기 전까지는 이 가설을 쓰지
않는다는 뜻이다.

### A4. 폐기한 주장들

세웠다가 버린 주장들이다. 원인별로 묶으면 네 갈래다.

**`EXPLAIN ANALYZE` 의 시간을 믿어서** —
"`ORDER BY` 를 빼면 1,185배 빨라진다"(실제로는 16~23초로 여전히 느리다),
"매치가 많아지면 행당 비용이 83배 악화된다", "매치 3,500~15,000건 구간에 절벽이 있다"
(근거가 무효일 뿐 절벽이 없다는 뜻은 아니다 — 그 구간에 측정점이 없다),
"34초의 범인은 행 페치"(실험 10에서 기각), "`created_at` 인덱스가 배포에 반영 안 됐다"
(`ALTER TABLE` 이 `Duplicate key name` 으로 실패 — 이미 있었다).

**`ORDER BY` 를 빼고 재서** —
"토큰 1개면 매치가 많아도 싸다"(운영 형태로 재니 30.50초), "지배 변수는 토큰 수다"
(정렬이 붙으면 매치 건수가 지배한다), "`ORDER BY` 는 2.3배 더하는 것"(`복식` 에서는
0.32초를 30초로 만든다). 대조군을 깔끔하게 만드는 것과 운영 쿼리를 재현하는 건 다른
일인데 전자만 하고 결론을 후자에 적용했다. 이후의 모든 측정은 운영과 같은
`ORDER BY created_at DESC, id DESC LIMIT 11` 로 했다.

**기각 근거를 잘못 골라서** —
덧셈 모델을 "`테니스` 가 44~56초여야 하는데 38.72초" 라며 기각했다가, 기준값에서 16초
갈래를 빼고 계산한 걸 발견하고 되살렸다(실험 8). 폐기 목록에 올리는 것도 새 주장을
세우는 것과 똑같이 틀릴 수 있다.

**편차보다 작은 차이로 모델을 세워서** —
매치당 0.50~0.93ms 같은 상수, 토큰 배수 1.5배, 덧셈이냐 배수냐 논쟁 전부. 같은 `복식` 이
22.97~30.50초로 흔들리는데 그 폭보다 작은 차이를 비교하고 있었다. 실험 10 이후 이 문서는
매치 건수의 자릿수만 말한다.

살아남은 근거는 전부 실제 소요 시간이나 HTTP 로 잰 것이다. `rows` 와 실행 계획,
에러 메시지는 처음부터 유효했다.

## 아직 확인 안 한 것

  무너지는지 모른다
