# 키워드 검색이 느린 문제 — 실험 기록

운영에서 키워드 검색이 34초 걸리는 걸 발견하고 원인을 좁혀간 기록이다.
**아직 해결하지 못했고**, 무엇이 원인이고 무엇이 안 되는지까지 확인한 상태다.

> ⚠️ **이 문서는 한 번 크게 다시 썼다.** 처음에는 `EXPLAIN ANALYZE` 가 알려준 시간을 근거로 결론을 세웠는데,
> 실제 소요 시간과 최대 234배까지 어긋난다는 걸 뒤늦게 확인했다. 폐기한 내용은 맨 뒤에 그대로 남긴다.

## 결론 먼저

- 비용을 정하는 건 **검색어가 몇 개 토큰으로 쪼개지느냐**와 **매치 건수**, 둘 다다.
  - 토큰 1개(2글자 검색어)면 매치가 **7만 건이어도 0.20초**. 매치 건수와 사실상 무관하다
  - 토큰 2개 이상이면 매치 건수에 **초선형**으로 비싸진다. `포핸드`(3,478건) 0.13초 → `테니스`(41,679건) **23초**
- `LIMIT` 은 아무 도움이 안 된다. FULLTEXT 는 매치 집합을 먼저 만들고 나서 행을 흘려보낸다.
- **MySQL 안에서 우회할 방법을 여섯 가지 시도해 전부 막혔다.** `FORCE INDEX` 는 `ERROR 1191` 로 문법 차원에서 거부된다.
- `LIKE` 로 되돌려도 답이 아니다. 최악 케이스가 정반대로 옮겨간다.

---

## 측정 방법에 대한 경고 (먼저 읽을 것)

**`EXPLAIN ANALYZE` 의 노드 시간을 FULLTEXT 쿼리에서 믿으면 안 된다.**

같은 출력 안에 증거가 있다.

```
-> Full-text index search on posts ...  (actual time=103..108 rows=11)   ← 108ms 라고 보고
...
1 row in set (25.29 sec)                                                 ← 이 문장이 실제로 25.29초 걸림
```

| 키워드 | 노드가 보고한 시간 | 문장의 실제 소요 시간 |
|---|---|---|
| `타이브레이크` | 0.191ms | 0.11초 |
| `포핸드` | 0.775ms | 0.09초 |
| `복식` | 13.4ms | 0.27초 |
| **`테니스`** | **108ms** | **25.29초** (234배) |

`EXPLAIN ANALYZE` 는 **반복자(iterator)가 도는 시간**을 잰다. 그런데 InnoDB FULLTEXT 는
반복자가 돌기 전에 엔진 내부에서 매치 집합을 만드는데, **그 준비 시간이 노드에 안 잡힌다.**

**`rows` 는 여전히 신뢰할 수 있다.** 실제로 처리한 행 수는 정확하다. `time` 만 버리면 된다.

**그리고 B-tree 스캔에서는 정확하다.** `LIKE '%테니스%'` 는 `EXPLAIN ANALYZE` 가 33.5ms 라고 했고
실제 소요도 0.02초로 거의 일치했다. 준비 단계가 따로 없는 접근 경로라 반복자 시간이 곧 전부이기 때문이다.
**문제는 FULLTEXT 에 한정된다.**

그래서 이 문서의 시간은 전부 **mysql 클라이언트가 찍어주는 실제 소요 시간**(`N rows in set (X sec)`)이다.

### 캐시 영향도 크다

| 키워드 | 1회차 | 2회차 |
|---|---|---|
| `포핸드` | **4.45초** | **0.13초** (34배) |
| `테니스` | 31.46초 | 23.27초 (1.35배) |
| `복식` | 0.33초 | 0.32초 |

**한 번만 재면 못 믿는다.** 이 문서의 값은 2회차(안정값) 기준이다.
`테니스` 가 반복해도 23초인 건 **작업 집합이 버퍼풀(128MB)에 안 들어가기 때문으로 보인다.**
`posts` 만 486MB 라 3.8배다. 다만 버퍼풀 히트율까지 재지는 않아 **정황이지 증명은 아니다.**

## 용어

| 용어 | 뜻 |
|---|---|
| 토큰 | 색인의 최소 단위. `ngram_token_size=2` 라 2글자씩 자른다. `테니스` → `[테니][니스]` |
| phrase 검색 | 따옴표로 감싸 토큰들이 **붙어 있는** 문서만 찾는 것. 토큰이 2개 이상일 때만 위치 대조가 필요하다 |
| 접근 경로 | 테이블에서 행을 꺼내는 통로. 인덱스마다 하나씩이고 쿼리당 보통 하나만 고른다 |
| 조기 종료 | 필요한 만큼(`LIMIT 11`) 찾으면 나머지를 안 보고 멈추는 것 |
| ttfb | 요청 후 응답 첫 바이트가 도착할 때까지의 시간 |

## 측정 환경

| 항목 | 내용 |
|---|---|
| 대상 | 운영 (EC2 nginx → backend → AWS RDS MySQL 8) |
| 데이터 | `bench/sql` 로 만든 모집글 100만 건 규모 (활성 940,445) |
| 인덱스 | `ft_posts_title_content (title, content) WITH PARSER ngram`, `ngram_token_size=2` |
| 페이지 | `size=10` → `LIMIT 11` |
| 버퍼풀 | **128MB** (`innodb_buffer_pool_size`) |
| `posts` 크기 | **486MB** (데이터+인덱스, FT 보조 테이블 제외) |

> ⚠️ **버퍼풀 128MB 는 운영치고 아주 작다.** 테이블이 그 3.8배라 데이터가 메모리에 안 들어간다.
> 그래서 **이 문서의 절대 시간은 이 환경의 값**이고, 버퍼풀이 크면 개선될 여지가 있다.
>
> 다만 **상대 비교는 유효하다.** `복식`(1토큰) 0.20초 vs `테니스`(2토큰) 23초는 같은 버퍼풀에서 난 차이고,
> `ORDER BY` 를 빼도 16초라는 것도, 우회 여섯 가지가 막힌 것도 환경과 무관하다.

## 문제 발견

| 요청 | ttfb |
|---|---|
| `?keyword=테니스&size=10` (첫 요청) | 41.38초 |
| `?keyword=테니스&size=10` (반복 3회) | 34.92 / 34.00 / 34.52초 |
| 조건 없음 (대조) | 0.090 / 0.117 / 0.112초 |

키워드가 붙은 요청만 느렸다. 코드를 보니 `keyword` 유무로 쿼리가 갈린다 — 있으면 FULLTEXT 네이티브 쿼리,
없으면 JPQL. **범위가 여기로 좁혀졌다.**

## 실험 1 — 요청 파라미터로 줄일 수 있나

가장 싼 것부터 확인했다.

| 물어본 것 | 어떻게 | 결과 |
|---|---|---|
| 10건 뽑느라 느린가 | `size=1` 로 축소 | **33.5초** (변화 없음) |
| 조건이 넓어서인가 | `category` 필터 추가 | **33.5초** (변화 없음) |

**둘 다 배제.** 비용이 반환 건수나 조건 개수와 무관하다.
→ HTTP 로는 더 못 좁힌다고 판단하고 SQL 로 내려갔다.

## 실험 2 — 규모를 정하는 변수 찾기

```sql
SELECT COUNT(*) FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE);
```

**41,679건.** 활성 940,445건 대비 약 4.4%.
11건 반환하려고 4만 건짜리 집합을 다루고 있었다.

## 실험 3 — `LIMIT` 은 왜 안 듣나

```sql
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
LIMIT 11;
```

**실제 소요: 15.5~16.4초** (연속 2회로 캐시 효과 아님을 확인).

`ORDER BY` 도 없고 행 페치도 없는데 16초다.

**해석**: InnoDB FULLTEXT 는 **매치 집합을 먼저 통째로 만들고 나서** 행을 흘려보낸다.
`LIMIT` 이 11이든 1이든 앞단 비용은 그대로다. **조기 종료라는 게 애초에 없다.**

## 실험 4 — `ORDER BY` 를 붙이면

| | 실제 소요 |
|---|---|
| `LIMIT 11` | 15.5~16.4초 |
| `ORDER BY id DESC LIMIT 11` | **36.15초** |

**약 2.3배.** `EXPLAIN ANALYZE` 의 `rows` 를 보면 이유가 보인다 — `ORDER BY` 가 없으면 FT 노드가
`rows=11`, 있으면 `rows=41679` 다. **정렬하려면 매치 전량의 `id` 를 확인해야 한다.**

정렬 연산 자체는 싸다(`Sort` 노드 92ms). 비싼 건 **정렬하려고 전량을 확인하는 것**이다.

## 실험 5 — 우회로가 있나

| 시도 | 결과 |
|---|---|
| 커서로 `id` 범위 제한 (`AND id > 990000`) | FT 노드 `rows=41679` 그대로. 조건은 뒤에서 420건으로 걸러짐 |
| 날짜 범위 결합 | FT `rows=41679` → 날짜 통과 475건. **오히려 악화** |
| `FORCE INDEX` 로 다른 인덱스 강제 | **`ERROR 1191 Can't find FULLTEXT index matching the column list`** |

`MATCH` 를 WHERE 에 쓰면 **FULLTEXT 인덱스가 접근 경로여야만 한다.**
"날짜로 먼저 좁히고 키워드는 행마다 검사" 라는 방식은 MySQL 에서 표현 자체가 안 된다.

**실험 1·3·4·5를 합치면 여섯 가지 우회가 전부 막혔다.**

## 실험 6 — 대조군: 무엇이 비용을 정하나

`bench/sql/03_words.sql` 이 주제별 단어에 가중치를 부여한다. **테니스 주제(topic 21)** 안에
빈도 계층이 있어서, 주제·문체를 고정하고 변수만 바꾼 대조군을 만들 수 있었다.

측정은 전부 `SELECT id ... LIMIT 11` 의 **2회차 실제 소요 시간**이다.

| 키워드 | 토큰 | 매치 | 시간 |
|---|---|---|---|
| `포핸드` | `[포핸][핸드]` 2개 | 3,478 | **0.13초** |
| `라켓` | `[라켓]` **1개** | **69,237** | **0.20초** |
| `타이브레이크` | `[타이][이브][브레][레이][이크]` 5개 | 99 | 0.26초 |
| `복식` | `[복식]` **1개** | **49,685** | 0.32초 |
| `테니스` | `[테니][니스]` 2개 | 41,679 | **23.27초** |

### 읽을 점 셋

**① 매치 건수만으로는 설명이 안 된다.** 매치가 가장 많은 `라켓`(69,237건)이 **가장 빠르다**(0.20초).
`테니스` 는 그보다 매치가 적은데(41,679건) 23초다.

**② 토큰 수만으로도 설명이 안 된다.** `포핸드` 와 `테니스` 는 똑같이 2토큰인데 0.13초와 23초다.

**③ 둘이 같이 작용한다.**

```
토큰 1개  →  phrase 검증이 없다. 목록만 읽으면 끝
             매치 건수와 사실상 무관 (49,685건 0.32초 / 69,237건 0.20초)

토큰 2개+ →  목록을 교차시키고 글자 위치가 인접한지 대조해야 한다
             매치 건수에 초선형 (3,478건 0.13초 / 41,679건 23초 — 12배 매치에 179배 시간)
```

`ngram_token_size=2` 라 **2글자 검색어는 토큰이 하나**가 되는 게 이 차이를 만든다.

### 여기서 파생되는 것

`ngram_token_size` 를 1로 낮추면 1글자 검색이 가능해지지만, **모든 다글자 검색어가 다토큰이 된다.**

```
token_size=2:  복식 → [복식]           1개
token_size=1:  복식 → [복][식]          2개
               테니스 → [테][니][스]     3개
```

지금 0.32초인 `복식` 이 `테니스` 쪽 특성으로 넘어간다는 뜻이다.
**1글자 검색을 살리면 나머지가 느려지는 맞바꿈**이다.

> 이건 **측정이 아니라 추론이다.** RDS 파라미터 변경 + FT 인덱스 재구축이 필요해 확인하지 못했다.

## 실험 7 — `LIKE` 와 비교

| 키워드 | LIKE | FULLTEXT |
|---|---|---|
| `테니스` (매치 41,679) | **0.02초** / 339행 | **23초** |
| `리그오브레전드` (매치 0) | **13,130ms** / 전량 | 0.013초 |

**같은 키워드에서 약 1,150배** 차이다.

`LIKE` 는 인덱스가 주는 순서를 그대로 걷다가 **339행에서 조기 종료**한다.
반대로 매치가 없으면 94만 행을 다 훑는다.

**두 방식의 최악 케이스가 정반대다.** `LIKE` 는 매치가 없을 때, FULLTEXT 는 매치가 많을 때 무너진다.
한쪽으로 되돌리는 건 문제를 옮기는 것에 가깝다.

> `LIKE` 는 `EXPLAIN ANALYZE`(33.5ms)와 실제 소요(0.02초)가 거의 일치했다.
> B-tree 스캔에는 FULLTEXT 같은 준비 단계가 없어서다.

## 종합 — 무엇이 배제됐나

| 시도 | 결과 |
|---|---|
| `LIMIT` 을 1로 축소 | 33.5초 (변화 없음) |
| `category` 필터 추가 | 33.5초 (변화 없음) |
| 행 페치 제거 (`SELECT id`) | 16초 |
| **`ORDER BY` 제거** | **16초 — 정렬을 포기해도 안 된다** |
| 커서로 id 범위 제한 | FT 가 41,679건 그대로 |
| 날짜 범위 결합 | 오히려 악화 |
| `FORCE INDEX` | `ERROR 1191` |

> **MySQL FULLTEXT 로는 토큰 2개 이상 + 매치가 많은 검색어에서 빠져나갈 구멍이 없다.**

특히 **`ORDER BY` 를 포기해도 16초**라는 게 크다. "최신순을 버리면 해결된다"는 탈출구가 없다.

## 남은 선택지

전부 뭔가를 포기해야 한다. 아직 어느 것도 구현·측정하지 않았다.

| 안 | 포기하는 것 | 근거가 되는 측정 |
|---|---|---|
| A. `ORDER BY` 를 버린다 | 최신순 정렬 | **없음.** 정렬을 빼도 16초 |
| B. LIKE 로 되돌린다 | FULLTEXT | 흔한 키워드 33.5ms, 없는 키워드 13,130ms |
| C. 검색엔진을 도입한다 | MySQL 단일 스택 | 없음 |

**A 는 실질적으로 죽었다.** 실험 3에서 정렬을 빼도 16초가 나오면서 근거가 사라졌다.

B 는 최악 케이스가 반대로 옮겨갈 뿐이다. 그리고 결과가 없는 검색(오타·없는 단어)은 실사용에서 흔하므로,
되돌리면 **더 자주 터지는 쪽**을 고르게 된다.

## 데이터셋의 성격

측정 대상은 `bench/sql` 이 만든 **합성 데이터**다. 본문 단어를 `03_words.sql` 의 가중치 풀에서 뽑아
조립하므로 키워드별 매치 건수가 그 생성 규칙으로 결정된다.

**실제 서비스 데이터에서 어떤 검색어가 몇 건에 매치될지는 이 문서로 알 수 없다.**
다만 **토큰 수는 데이터와 무관하다** — 2글자냐 3글자냐는 검색어의 성질이라, 그 부분은 그대로 적용된다.

## 폐기된 내용 (한 번 틀렸던 것)

투명하게 남긴다. 전부 `EXPLAIN ANALYZE` 의 시간을 믿어서 생긴 오류다.

| 폐기된 주장 | 왜 틀렸나 |
|---|---|
| "`ORDER BY` 가 조기 종료를 막는다. 빼면 21,573ms → 18.2ms, **1,185배**" | 실제로는 16초. `ORDER BY` 는 16초 → 36초로 **2.3배** 더할 뿐이다 |
| "매치가 많아지면 **행당 비용이 83배** 악화된다" | `EXPLAIN ANALYZE` 숫자끼리 비교한 착시. 실제로는 토큰 수가 지배 변수다 |
| "매치 3,500~15,000건 구간에 **절벽**이 있다" | `복식`(49,685건)이 0.32초로 나오면서 무너졌다 |
| "34초의 범인은 41,679번의 **행 페치**" | `SELECT id` 로 행 페치를 없애도 16초 |
| "`created_at` 인덱스가 **배포에 반영 안 됐다**" | `ALTER TABLE` 이 `Duplicate key name` 으로 실패. 이미 있었다 |

**살아남은 근거는 전부 실제 소요 시간이나 HTTP 로 잰 것**이고, 무너진 건 전부 `EXPLAIN ANALYZE` 시간에
기댄 것이었다. `rows` 와 실행 계획, 에러 메시지는 처음부터 지금까지 유효하다.

## 아직 확인 안 한 것

- **배포 후 키워드 검색의 HTTP 응답 시간.** 34초는 복합 커서 배포 **이전** 값이다.
  지금은 네이티브 쿼리의 `ORDER BY` 도 `created_at DESC, id DESC` 로 바뀌었으므로 다시 재야 한다
- `ngram_token_size=1` 로 낮췄을 때의 실제 영향. 파라미터 변경 + 인덱스 재구축이 필요해 **추론으로만 남긴다**
- `테니스` 가 23초인 것이 버퍼풀 때문이라는 **증명**. 정황(486MB vs 128MB)까지만 확인했고
  히트율은 재지 않았다
- 버퍼풀이 큰 환경에서의 절대값. 이 문서의 시간은 128MB 환경의 값이다

### 확인할 수 없는 것

- **실제 서비스 데이터의 검색어별 매치 건수 분포.** 개인 프로젝트라 실사용자가 없어 관측할 방법이 없다.
  다만 **토큰 수는 데이터와 무관하다** — 2글자냐 3글자냐는 검색어 자체의 성질이므로
  그 부분의 결론은 실데이터에도 그대로 적용된다
