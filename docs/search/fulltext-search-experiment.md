# 키워드 검색이 느린 문제 — 실험 기록

운영에서 키워드 검색이 34초 걸리는 걸 발견하고, 원인을 좁혀가며 돌린 실험을 순서대로 남긴다.
**아직 해결하지 못했고**, 무엇이 원인이고 무엇이 안 되는지까지 확인한 상태다.

각 실험은 **무엇을 확인하려 했는지 → 어떻게 쟀는지 → 결과 → 무슨 뜻인지** 순으로 적는다.

## 결론 먼저

- FULLTEXT 자체는 빠르다. 같은 쿼리에서 `ORDER BY` 만 빼면 **21,573ms 가 18.2ms** 로 끝난다.
- 느린 이유는 **최신순 정렬 요구가 매치 전량을 받게 만들기** 때문이다. `테니스` 는 매치가 41,679건이다.
- 매치가 적으면 멀쩡하다. 3,478건이면 0.15초, 99건이면 0.10초, 0건이면 0.06초다.
- **MySQL 안에서 우회할 방법은 여섯 가지를 시도해 전부 막혔다.**
- `LIKE` 로 되돌려도 답이 아니다. 같은 환경에서 재보니 **최악 케이스가 정확히 반대**다
  (흔한 키워드 33.5ms / 없는 키워드 13,130ms).

## 읽기 전에

### 용어

| 용어 | 뜻 |
|---|---|
| 접근 경로 | 테이블에서 행을 꺼내는 통로. 인덱스마다 하나씩이고 쿼리당 보통 하나만 고른다 |
| 조기 종료 | 필요한 만큼(`LIMIT 11`) 찾으면 나머지를 안 보고 멈추는 것. 이 문서의 핵심 개념 |
| 스트리밍 | 결과를 다 모아서 주지 않고 찾는 대로 하나씩 흘려보내는 방식 |
| 행 페치 | 인덱스로 위치를 찾은 뒤 실제 테이블 행을 읽어오는 것 |
| ngram 파서 | 띄어쓰기로 단어를 못 나누는 언어를 위해 글자를 N개씩 잘라 색인하는 방식. 여기선 2글자 |
| phrase 검색 | 따옴표로 감싸 토큰들이 붙어 있는 문서만 찾는 것 |
| ttfb | 요청 후 응답 첫 바이트가 도착할 때까지의 시간 |

### `EXPLAIN ANALYZE` 출력 읽는 법

```
-> Limit: 11 row(s)                            (actual time=21572..21573 rows=11 loops=1)
    -> Sort row IDs: posts.id DESC             (actual time=21571..21572 rows=11 loops=1)
        -> Filter: (match ...)                 (actual time=13.4..21479  rows=41679 loops=1)
            -> Full-text index search on posts (actual time=12.4..21434  rows=41679 loops=1)
```

- **안쪽이 먼저 실행되고 바깥으로 흘러간다.** 가장 안쪽이 출발점, 맨 위 `Limit` 이 종착점이다.
- `actual time=A..B` 에서 **A 는 첫 행이 나온 시각, B 는 마지막 행까지 끝난 시각**(ms).
- **가장 안쪽 노드의 `rows` 가 실제로 읽은 행 수**, 그 위 `Filter` 의 `rows` 가 조건을 통과한 행 수다.
  둘의 차이가 **버린 행**이다. (PostgreSQL 의 `Rows Removed by Filter` 에 해당)
- `(cost=... rows=...)` 는 옵티마이저 **추정치**라 실제와 다를 수 있다. `actual` 을 봐야 한다.

## 실험 1 — 반환 건수를 줄이면 빨라지나?

**확인하려던 것**: "10건 뽑느라 느린 거면 1건만 뽑으면 빨라지지 않을까."

**방법**: `size` 파라미터만 바꿔 요청.

| 요청 | ttfb |
|---|---|
| `keyword=테니스&size=10` | 34.0초 |
| `keyword=테니스&size=1` | **33.5초** |

**해석**: 안 줄었다. 비용이 "반환할 건수"와 무관하다는 뜻이다.
→ 반환 건수가 아니라 **처리하는 전체 집합**에 비용이 있다.

## 실험 2 — 조건을 더 걸어 범위를 좁히면?

**확인하려던 것**: 결과가 줄면 일이 줄어들까.

**방법**: `category` 필터를 추가.

| 요청 | ttfb |
|---|---|
| `keyword=테니스` | 34.0초 |
| `keyword=테니스&category=EXERCISE` | **33.5초** |

**해석**: 역시 안 줄었다. 요청 파라미터로 피할 수 있는 비용이 아니다.
→ 여기서 HTTP 측정으로는 더 좁힐 수 없다고 판단하고 SQL 로 내려갔다.

## 실험 3 — 매치가 몇 건인가?

**확인하려던 것**: 비용의 크기를 정하는 변수를 찾기.

```sql
SELECT COUNT(*) FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE);
```

**결과**: **41,679건**. 활성 940,445건 대비 약 4.4%.

**해석**: 11건 반환하려고 4만 건짜리 집합을 다루고 있었다.

## 실험 4 — 행을 안 읽으면 빨라지나?

**확인하려던 것**: 41,679건의 **행을 실제로 읽는 비용**이 범인인지.
`deleted`/`blinded` 조건은 인덱스에 없어서 행을 꺼내야 검사할 수 있다. 그걸 다 빼봤다.

```sql
EXPLAIN ANALYZE
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
ORDER BY id DESC LIMIT 11;
```

```
-> Limit: 11 row(s)                                      (actual time=21572..21573 rows=11)
    -> Sort row IDs: posts.id DESC                       (actual time=21571..21572 rows=11)
        -> Filter: (match ...)                           (actual time=13.4..21479  rows=41679)
            -> Full-text index search                    (actual time=12.4..21434  rows=41679)
```

**결과**: 21,573ms. 행 페치를 전부 없앴는데도 21.5초다.

| 노드 | 비용 |
|---|---|
| `Full-text index search` | 12.4ms → **21,434ms** (41,679행) |
| `Filter` (재확인) | +45ms |
| `Sort` | **+92ms** |

**해석**: **정렬 연산 자체는 92ms 밖에 안 된다.** 비용은 전부 FT 노드가 41,679건을 뽑는 데 있다.
그리고 FT 노드의 `12.4..21434` 에서 앞의 12.4ms 가 **첫 행이 나온 시각**이라는 게 눈에 띈다.
검색은 빠르게 시작하는데 끝까지 뽑는 데 21초가 걸린 것이다.

→ 그럼 왜 끝까지 뽑아야 하지? 라는 질문이 나온다.

## 실험 5 — `ORDER BY` 를 빼면? (결정적)

**확인하려던 것**: 전량을 뽑는 이유가 정렬 요구 때문인지.

```sql
EXPLAIN ANALYZE
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
LIMIT 11;
```

```
-> Limit: 11 row(s)                     (actual time=13.3..18.2 rows=11)
    -> Filter: (match ...)              (actual time=12.2..17.2 rows=11)
        -> Full-text index search       (actual time=11.4..16.4 rows=11)
```

| | FT 가 뽑은 행 | 시간 |
|---|---|---|
| `ORDER BY id DESC LIMIT 11` | 41,679 | 21,573ms |
| `LIMIT 11` | **11** | **18.2ms** |

**결과**: **1,185배.** FT 는 11건에서 멈췄다.

**해석**: 원인이 확정됐다. FULLTEXT 는 원래 스트리밍이라 조기 종료가 가능한데,
**`ORDER BY` 가 붙으면 정렬하려고 입력을 끝까지 소진해야** 해서 그 능력이 죽는다.

왜 정렬을 못 피하냐면, FULLTEXT 에는 **정렬 개념이 없기** 때문이다.
`SHOW INDEX FROM posts` 를 보면 B-tree 인덱스는 `Collation` 이 `A`(오름차순)인데
`ft_posts_title_content` 는 `NULL` 이다. 줄이 서 있지 않으니 최신순 11건을 고르려면 전부 받아 세워야 한다.

## 실험 6 — 커서로 범위를 제한하면?

**확인하려던 것**: `id` 범위를 주면 FT 가 그만큼만 뽑아줄까.

```sql
EXPLAIN ANALYZE
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
  AND id > 990000
ORDER BY id DESC LIMIT 11;
```

```
-> Filter: (match ... and (id > 990000))   (actual time=114..21570 rows=420)
    -> Full-text index search              (actual time=69.5..21514 rows=41679)
```

**결과**: FT 는 여전히 41,679건을 뽑았다. `id` 조건은 그 **뒤에** 적용돼 420건으로 걸러졌다. 21.6초.

**해석**: 커서나 범위 조건으로는 FT 의 작업량을 못 줄인다. 항상 다 만들고 나서 거른다.

**곁다리 발견**: `Filter` 의 첫 행이 114ms 에 나왔다. `id > 990000` 인 행은 전체 매치의 1%뿐인데
스트림 맨 앞에서 나왔다는 뜻이라, **FT 의 반환 순서는 `id` 오름차순이 아니다.**

## 실험 7 — 매치 건수를 바꿔가며 (대조군)

**확인하려던 것**: 비용이 매치 건수에 비례하는지.

`bench/sql/03_words.sql` 은 주제별 단어에 가중치를 부여한다. **테니스 주제(topic 21)** 안에
빈도 계층이 그대로 있어서, 주제와 문체를 고정한 채 매치 건수만 바꾼 대조군을 만들 수 있었다.

| 키워드 | weight | 매치 건수 | FT 노드 시간 | 행당 | HTTP |
|---|---|---|---|---|---|
| `리그오브레전드` | 없는 단어 | **0** | 0.005ms | — | **0.058초** |
| `타이브레이크` | 1 | **99** | 0.80ms | 0.0081ms | **0.102초** |
| `포핸드` | 40 | **3,478** | 21.6ms | 0.0062ms | **0.151초** |
| `복식` | 200 | 미측정 | — | — | **23.3초** |
| `라켓` | 800 | 미측정 | — | — | **30.1초** |
| `테니스` | 3000 | **41,679** | 21,434ms | **0.514ms** | **34.0초** |

**해석**:

- **모든 키워드가 느린 게 아니다.** 3,478건까지는 0.15초로 멀쩡하다.
- **비례하지 않는다.** 매치가 12배(3,478 → 41,679) 늘 때 시간은 992배 뛴다. 행당 비용 자체가 83배 나빠진다.
- **절벽이 weight 40 과 200 사이에 있다.** 0.15초와 23초 사이에 중간 지대가 거의 없다.
- 매치 0건이 가장 빠르다(0.058초). 뒤에서 보겠지만 `LIKE` 는 이 경우가 최악이었다.

행당 비용이 왜 83배나 뛰는지는 **규명하지 못했다.** 확인한 건 "매치가 많아지면 건당 비용이 나빠진다"까지다.

## 실험 8 — 날짜 범위를 결합하면?

**확인하려던 것**: 날짜 범위 검색은 `ORDER BY` 를 `created_at` 기준으로 바꿔서 4,000배 빨라졌다
(`date-range-search-troubleshooting.md`). 키워드에도 같은 수가 통할지, 즉 날짜 조건과 정렬이
둘 다 `created_at` 이면 옵티마이저가 FT 대신 `created_at` 인덱스를 고를지 확인했다.

```sql
EXPLAIN ANALYZE
SELECT p.* FROM posts p
WHERE MATCH(p.title, p.content) AGAINST('"테니스"' IN BOOLEAN MODE)
  AND p.created_at >= '2023-07-01' AND p.created_at < '2023-08-01'
  AND p.deleted = 0 AND p.blinded = 0
ORDER BY p.created_at DESC, p.id DESC LIMIT 11;
```

```
-> Limit: 11 row(s)                        (actual time=25663..25667 rows=11)
    -> Sort row IDs: created_at DESC, id DESC  (actual time=25662..25666 rows=11)
        -> Filter: (blinded=0 and deleted=0 and match ... and created_at >= ... and < ...)
                                           (actual time=113..25589   rows=475)
            -> Full-text index search      (actual time=20.9..25426  rows=41679)
```

**결과**: 실패. FT 가 또 41,679건을 뽑았고, 날짜 조건은 뒤에서 475건으로 걸렀다. **25,667ms.**

| | |
|---|---|
| FT 가 만든 매치 | 41,679 |
| 날짜 조건 통과 | 475 |
| **버린 행** | **41,204 (98.9%)** |

**해석**: 날짜 범위 검색을 살린 수가 키워드에는 안 통한다. `created_at` 인덱스는 **후보에도 안 올라간다.**
그리고 조건이 하나 늘어난 만큼 **오히려 더 느려졌다**(21.6초 → 25.7초). 41,679건 각각에 날짜 비교가 붙어서다.

## 실험 9 — 강제로도 안 되나?

**확인하려던 것**: 옵티마이저가 안 고르는 거라면 강제하면 되지 않을까.

```sql
EXPLAIN ANALYZE
SELECT p.* FROM posts p FORCE INDEX (idx_posts_created_at_deleted_blinded)
WHERE MATCH(p.title, p.content) AGAINST('"테니스"' IN BOOLEAN MODE)
  AND p.created_at >= '2023-07-01' AND p.created_at < '2023-08-01'
  ...
```

**결과**:

```
ERROR 1191 (HY000): Can't find FULLTEXT index matching the column list
```

**해석**: `MATCH` 를 WHERE 에 쓰면 FULLTEXT 인덱스가 **접근 경로여야만** 한다.
"날짜로 먼저 좁히고 키워드는 행마다 검사" 라는 방식은 MySQL 에서 **표현 자체가 불가능**하다.

## 실험 10 — 같은 환경에서 LIKE 와 비교

**확인하려던 것**: 지금까지 `LIKE` 숫자는 **로컬 + 옛 정렬(`ORDER BY id DESC`)** 기준이라
운영의 FULLTEXT 34초와 직접 비교가 안 됐다. 같은 RDS 에서 같은 정렬로 재봤다.

```sql
-- 흔한 키워드
EXPLAIN ANALYZE
SELECT p.* FROM posts p
WHERE (p.title LIKE '%테니스%' OR p.content LIKE '%테니스%')
  AND p.deleted = 0 AND p.blinded = 0
ORDER BY p.created_at DESC, p.id DESC LIMIT 11;
```

```
-> Limit: 11 row(s)                                       (actual time=13.6..33.5 rows=11)
    -> Filter: (blinded=0 and deleted=0 and (title like ... or content like ...))
                                                          (actual time=12.8..32.8 rows=11)
        -> Index scan on p using idx_posts_created_at_deleted_blinded (reverse)
                                                          (actual time=9.81..32.4 rows=339)
```

**결과**:

| 키워드 | 방식 | 읽은 행 | 시간 |
|---|---|---|---|
| `테니스` (매치 41,679) | LIKE | **339** | **33.5ms** |
| `테니스` | FULLTEXT | 41,679 | 21,573ms |
| `리그오브레전드` (매치 0) | LIKE | 940,445 (전량) | **13,130ms** |
| `리그오브레전드` | FULLTEXT | 0 | **13ms** |

**해석**:

- **흔한 키워드에서는 LIKE 가 644배 빠르다.** `ORDER BY created_at DESC` 를 우리 인덱스가 만족시켜주니
  `LIKE` 는 걸으면서 검사하다 11건을 채우고 **339행에서 멈춘다.** FULLTEXT 는 이 "멈추기"가 안 된다.
- **없는 키워드에서는 FULLTEXT 가 1,000배 빠르다.** 매치가 0이라 조기 종료가 안 되고 94만 행을 다 훑는다.
- **서로 정확히 반대다.** 한쪽이 630배 빠르면 다른 쪽에서 1,000배 느리다.

로컬에서 쟀던 337행과 운영의 339행이 거의 일치한다. 환경이 달라도 **읽는 행 수는 같다**는 게 확인됐다.

**예상 밖의 것**: 행당 비용이 오히려 `LIKE` 가 싸다. TEXT 컬럼을 통째로 뒤지는 쪽이
색인을 읽는 쪽보다 5배 싸다는 건 직관과 반대인데, 실험 7 의 "매치가 많아지면 행당 비용이 나빠진다"와
같은 미규명 현상으로 보인다.

| | 행당 |
|---|---|
| LIKE (행 조회 + TEXT 매칭) | 0.099ms |
| FULLTEXT | 0.514ms |

## 종합 — 무엇이 배제됐나

| 시도 | 결과 |
|---|---|
| `LIMIT` 을 1로 축소 | 33.5초 (변화 없음) |
| `category` 필터 추가 | 33.5초 (변화 없음) |
| 행 페치 제거 (`SELECT id`) | 21.5초 |
| 커서로 id 범위 제한 | FT 가 41,679건 그대로 |
| 날짜 범위 + `created_at` 정렬 | 25.7초 (오히려 악화) |
| `FORCE INDEX` 로 다른 인덱스 강제 | `ERROR 1191` |
| **`ORDER BY` 제거** | **18.2ms** |

> **MySQL FULLTEXT 로는 "키워드 검색 + 최신순 정렬"에서 조기 종료를 만들 방법이 없다.**

날짜 범위 검색은 정렬 축을 인덱스 순서에 맞춰서 풀렸지만, FULLTEXT 에는 맞출 순서 자체가 없어서 같은 수가 안 통한다.

## LIKE 와의 비교

실험 10 에서 같은 환경·같은 정렬로 쟀다. 전환 전 로컬 기록도 참고로 남긴다.

| 키워드 | LIKE (운영) | FULLTEXT (운영) | LIKE (로컬, 전환 전) |
|---|---|---|---|
| `테니스` (흔함) | **33.5ms** / 339행 | 21,573ms / 41,679행 | 12.2ms / 337행 |
| `리그오브레전드` (없음) | **13,130ms** / 전량 | 13ms / 0행 | 988ms / 100만행 |

### 왜 LIKE 가 빨랐나

검색 방식의 우열이 아니라 **정렬 방향과 스캔 방향이 맞았느냐**의 차이였다.

| | 결과를 내보내는 순서 | `ORDER BY id DESC` | 조기 종료 |
|---|---|---|---|
| LIKE | PK 역순 = `id` 내림차순 | 이미 만족 | **가능** (337행에서 종료) |
| FULLTEXT | `id` 내림차순이 **아님** | 전량 정렬 필요 | **불가** (41,679행 전부) |

그리고 **두 방식의 최악 케이스가 정반대**다. `LIKE` 는 매치가 없을 때 100만 행 풀스캔으로 무너지고,
FULLTEXT 는 매치가 많을 때 무너진다. 한쪽으로 되돌리는 건 문제를 옮기는 것에 가깝다.

## 데이터셋의 성격

측정 대상은 `bench/sql` 이 만든 **합성 데이터**다. 본문 단어를 `03_words.sql` 의 가중치 풀에서 뽑아
조립하므로 키워드별 매치 건수가 그 가중치로 결정된다. `테니스` 의 4.4% 도 실제 글에서 관측된
밀도가 아니라 생성 규칙의 결과다.

**실제 서비스 데이터에서 어떤 키워드가 몇 건에 매치될지는 이 문서로 알 수 없다.**
따라서 "34초가 실서비스에서도 나타나는가"는 여기서 답하지 않는다.

## 남은 선택지

전부 뭔가를 포기해야 한다. 아직 어느 것도 구현·측정하지 않았다.

| 안 | 포기하는 것 | 근거가 되는 측정 |
|---|---|---|
| A. `ORDER BY` 를 버린다 | 최신순 정렬 | `ORDER BY` 제거 시 18.2ms (실험 5) |
| B. LIKE 로 되돌린다 | FULLTEXT | 흔한 키워드 33.5ms, 없는 키워드 13,130ms (실험 10) |
| C. 검색엔진을 도입한다 | MySQL 단일 스택 | 없음 |

A 는 정렬 순서가 바뀌므로 `nextCursor` 계약과 프론트가 함께 바뀐다. 게다가 실험 6 에서 FT 의
반환 순서가 `id` 순이 아님이 드러나, `ORDER BY` 를 그냥 빼면 페이지네이션이 불안정해진다.

B 는 최악 케이스가 반대로 옮겨갈 뿐이다. 그리고 **어느 쪽이 더 아픈지는 어떤 검색이 더 자주 일어나느냐**로 갈리는데,
결과가 없는 검색(오타·없는 단어·너무 구체적인 조건)은 실사용에서 흔하다. 반면 매치가 4만 건인 키워드는
데이터가 그렇게 생겼을 때만 나온다. 즉 되돌리면 **더 자주 터지는 쪽**을 고르게 된다.

C 는 이 문제의 정석 해법이다. Elasticsearch 의 index sorting 은 색인 자체를 정렬해두는 기능이라,
**우리가 날짜 범위 검색에서 손으로 한 일(정렬 축을 색인 순서에 맞추기)을 엔진 차원에서 제공한다.**
다만 색인 동기화·정합성·운영 부담이 세트로 따라오고, 현재 인프라가 EC2 한 대라 비용도 붙는다.

**결정은 미결로 둔다.** 실서비스 데이터에서 재현되는지 먼저 보는 게 순서다.

## 아직 확인 안 한 것

- `복식`(weight 200)·`라켓`(weight 800)의 매치 건수. HTTP 시간만 있어서 절벽 위치를 정확히 못 박았다.
- 매치 건수가 늘 때 **행당 비용이 83배 악화되는 원인**. 미규명이다.
  (참고 관측: 같은 키워드라도 첫 실행 2.52초 → 직후 재실행 26ms 로 크게 달라진다)
- FULLTEXT 가 결과를 **실제로 어떤 순서로 내보내는지**. 실험 6 에서 "`id` 오름차순은 아니다"까지만 확인했다.
  `ORDER BY` 없이 반환된 `id` 를 보면 알 수 있다.
- 운영 RDS 의 인스턴스 클래스와 `innodb_buffer_pool_size`.
- 실제 서비스 데이터에서 키워드별 매치 건수 분포.
