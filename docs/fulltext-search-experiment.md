# FULLTEXT 키워드 검색과 `ORDER BY id DESC`

성능 측정 실험 기록이다. 프로덕션 기능 변경이 아니며, 이 문서 자체도 결과 아카이빙 목적이다.
`docs/created-at-index-experiment.md`(날짜 범위 인덱스 실험)의 후속이다.

> 용어가 낯설면 **[읽기 전에 — 비유와 용어](#읽기-전에--비유와-용어)** 를 먼저 보면 된다.
> 비유 한 문단 + 용어표 + `EXPLAIN ANALYZE` 출력 읽는 법이 있다.

## 요약

운영에서 키워드 검색이 **34초** 걸린다. 원인은 FULLTEXT 가 느려서가 아니라 **`ORDER BY id DESC` 가 조기 종료를 막기 때문**이다.
같은 쿼리에서 `ORDER BY` 만 제거하면 **21,573ms → 18.2ms(1,185배)** 로 떨어진다.

측정으로 확인한 것은 이것이다 — `ORDER BY id DESC` 가 붙으면 FULLTEXT 검색 노드가 **매치 41,679건을 전부** 뽑고,
빼면 **11건**에서 멈춘다. 즉 FULLTEXT 가 결과를 내보내는 순서는 `id` 내림차순이 아니며,
그래서 최신 11건을 고르려면 전량을 받아야 한다. `LIMIT` 을 줄여도 이 비용은 줄지 않는다.

그리고 그 "전량 받기" 비용은 매치 건수에 **선형이 아니다.** 3,478건에서 0.15초인데 그 위 구간에서 23초로 뛴다(4절).

> 이 문서는 **실측만** 담는다. 원인 설명이나 일반화가 필요한 항목은 맨 끝 "열린 항목" 으로 뺐다.

## 읽기 전에 — 비유와 용어

### 한 문단 비유

도서관에서 "테니스"가 나오는 책 중 **최신 11권**을 찾는다고 하자.

- **LIKE 방식**: 신간부터 한 권씩 펴서 "테니스"가 있나 본다. 11권 채우면 멈춘다.
  테니스 책이 흔하면 337권만 펴보고 끝난다. 대신 **한 권도 없는 단어**면 100만 권을 다 펴봐야 안다.
- **FULLTEXT 방식**: 색인 카드로 "테니스" 책 목록을 한 번에 뽑는다. 여기까지는 빠르다.
  문제는 카드가 **최신순으로 꽂혀 있지 않다**는 것 — "최신 11권"을 알려면 **카드 41,679장을 끝까지 다 뽑아야** 한다.
  (실제로 어떤 순서로 꽂혀 있는지는 이 문서에서 확인하지 않았다.)

이 문서는 두 번째 방식이 왜 34초가 되는지, 그리고 "최신순"이라는 요구만 빼면 왜 18ms 로 끝나는지를 측정한 기록이다.

### 용어

| 용어 | 뜻 |
|---|---|
| 실행 계획 | DB 가 쿼리를 처리하려고 세운 작업 순서 |
| `EXPLAIN ANALYZE` | 실행 계획을 **실제로 돌려보고** 단계별 시간·행 수까지 알려주는 명령. 진짜 실행되므로 느린 쿼리는 느리게 끝난다 |
| 노드 | 실행 계획의 한 단계(인덱스 읽기 / 필터 / 정렬 / LIMIT …) |
| 조기 종료 | 필요한 만큼(`LIMIT 11`) 찾으면 나머지를 안 보고 멈추는 것. 이 문서의 핵심 개념 |
| 스트리밍 | 결과를 다 모아서 주지 않고, 찾는 대로 하나씩 흘려보내는 방식 |
| 행 페치 | 인덱스로 위치를 찾은 뒤 **실제 테이블 행**을 읽어오는 것 |
| PK 역순 스캔 | 기본키(`id`) 인덱스를 큰 값부터 거꾸로 훑는 것. `ORDER BY id DESC` 와 방향이 같다 |
| 옵티마이저 | 어떤 인덱스를 쓸지 DB 가 알아서 고르는 부분. **비용을 추정**해 고르므로 틀릴 수 있다 |
| cold / warm | 캐시가 빈 첫 실행 / 캐시가 채워진 뒤의 반복 실행 |
| ttfb | Time To First Byte. 요청 후 응답 첫 바이트가 도착할 때까지의 시간 |
| ngram 파서 | 띄어쓰기로 단어를 못 나누는 언어를 위해 글자를 N개씩 잘라 색인하는 방식. 여기선 2글자 |
| 토큰 | 색인의 최소 단위. `테니스` → `테니`, `니스` |
| phrase 검색 | 따옴표로 감싸 토큰들이 **붙어 있는** 문서만 찾는 것 |
| 오버페치 | 필요한 것보다 1건 더 가져와(`LIMIT 11`) 다음 페이지 존재 여부를 판단하는 기법 |

### `EXPLAIN ANALYZE` 출력 읽는 법

```
-> Limit: 11 row(s)                            (actual time=21572..21573 rows=11 loops=1)
    -> Sort row IDs: posts.id DESC             (actual time=21571..21572 rows=11 loops=1)
        -> Filter: (match ...)                 (actual time=13.4..21479  rows=41679 loops=1)
            -> Full-text index search on posts (actual time=12.4..21434  rows=41679 loops=1)
```

- **안쪽이 먼저 실행되고 바깥으로 흘러간다.** 가장 안쪽(FULLTEXT 검색)이 출발점, 맨 위 `Limit` 이 종착점이다.
- `actual time=A..B` 에서 **A = 첫 행을 내보낸 시각, B = 마지막 행까지 끝난 시각**(단위 ms).
  `12.4..21434` 는 "12ms 만에 첫 결과가 나왔지만, 전부 뽑는 데 21.4초 걸렸다" 는 뜻이다.
- **시간은 누적이라 자식 노드를 포함한다.** 그 단계만의 비용은 부모 B − 자식 B 로 계산한다.
  예: 정렬 비용 = 21,571 − 21,479 = **92ms**.
- `rows` 는 그 노드가 내보낸 행 수, `loops` 는 실행 횟수(1이면 한 번).

## 측정 환경

| 항목 | 내용 |
|---|---|
| 대상 | 운영 (EC2 nginx → backend → **AWS RDS MySQL 8**) |
| 데이터 | `bench/sql` 로 생성한 모집글 100만 건 규모 |
| 인덱스 | `ft_posts_title_content (title, content) WITH PARSER ngram`, `idx_posts_created_at_deleted_blinded` **둘 다 적용됨** |
| 페이지 | `size=10` → `LIMIT 11`(오버페치 1건으로 `hasNext` 판정) |
| HTTP 측정 | `curl -w %{time_starttransfer}`, cold 1회 + warm 3회 |
| SQL 측정 | RDS 에 직접 접속해 `EXPLAIN ANALYZE` |

> 인덱스 적용 여부는 추측이 아니라 확인된 사실이다. `ALTER TABLE ... ADD INDEX idx_posts_created_at_deleted_blinded`
> 가 `ERROR 1061 Duplicate key name` 으로 실패했고, `MATCH ... AGAINST` 가 `ERROR 1191` 없이 결과를 반환했다.
> (FULLTEXT 인덱스가 없으면 `MATCH` 는 결과 대신 1191 로 즉시 실패한다.)

## 1. HTTP 응답 시간 (운영)

| 요청 | ttfb |
|---|---|
| `keyword=테니스&size=10` (cold) | 41.38s |
| `keyword=테니스&size=10` (warm ×3) | 34.92 / 34.00 / 34.52s |
| `keyword=테니스&size=1` | 33.50s |
| `keyword=테니스&category=EXERCISE` | 33.49s |
| `keyword=테` (1글자) | 0.13s · **0건** |
| 조건 없음 (×3) | 0.090 / 0.117 / 0.112s |
| `from=2023-07-01&to=2023-08-01` | 6.39s |
| `from=2026-08-01&to=2026-08-15` | 0.12s |

읽을 점 두 가지.

- **`size` 를 10 → 1 로 줄여도, 필터를 더해도 비용이 안 줄어든다.** 요청 파라미터로 피할 수 없는 비용이라는 뜻이다.
- **1글자 키워드는 0건이다.** `ngram_token_size=2` 라 토큰이 만들어지지 않는다. `docs/api-specification.md` 의
  keyword 설명("부분 일치")과 어긋나는 지점이다.

키워드 빈도를 바꿔가며 잰 결과는 4절에 따로 정리했다. **모든 키워드가 느린 것이 아니다** — `테니스` 가 특별히 나쁜 경우다.

## 2. 34초의 분해

`deleted`/`blinded` 와 행 페치를 모두 뺀 최소 형태로 좁혀도 21.5초다.

```sql
EXPLAIN ANALYZE
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
ORDER BY id DESC LIMIT 11;
```

```
-> Limit: 11 row(s)  (actual time=21572..21573 rows=11 loops=1)
    -> Sort row IDs: posts.id DESC, limit input to 11 row(s) per chunk  (actual time=21571..21572 rows=11 loops=1)
        -> Filter: (match ... against ('"테니스"' in boolean mode))  (actual time=13.4..21479 rows=41679 loops=1)
            -> Full-text index search on posts using ft_posts_title_content  (actual time=12.4..21434 rows=41679 loops=1)
```

| 노드 | 비용 | 해석 |
|---|---|---|
| `Full-text index search` | 12.4ms → **21,434ms**, 41,679행 | 전부 여기서 소비된다 |
| `Filter (match ...)` | +45ms | 재확인, 무시 가능 |
| `Sort row IDs: id DESC` | **+92ms** | 정렬 연산 자체는 싸다 |

`SELECT COUNT(*) ... MATCH(...)` = **41,679건**.

전체 쿼리(`SELECT p.*` + `deleted`/`blinded` + `JOIN members`)는 HTTP 기준 34초, 이 최소 형태는 SQL 기준 21.5초다.
**측정 지점이 달라 차이를 어느 단계에 귀속시킬 수는 없다.** 다만 행 페치를 전부 없앤 형태에서도 21.5초가 나온다는 것은 확인됐다.

## 3. `ORDER BY` 를 빼면

```sql
EXPLAIN ANALYZE
SELECT id FROM posts
WHERE MATCH(title, content) AGAINST('"테니스"' IN BOOLEAN MODE)
LIMIT 11;
```

```
-> Limit: 11 row(s)  (actual time=13.3..18.2 rows=11 loops=1)
    -> Filter: (match ...)  (actual time=12.2..17.2 rows=11 loops=1)
        -> Full-text index search on posts using ft_posts_title_content  (actual time=11.4..16.4 rows=11 loops=1)
```

| | FT 노드가 뽑은 행 | 총 시간 |
|---|---|---|
| `ORDER BY id DESC LIMIT 11` | 41,679 | 21,573ms |
| `LIMIT 11` | **11** | **18.2ms** |

FT 노드의 `actual time=12.4..21434` 에서 앞의 12.4ms 는 **첫 행까지** 걸린 시간이다.
검색은 원래 스트리밍이고 첫 결과는 12ms 만에 나온다. 21초는 41,679건을 *끝까지* 뽑느라 든 시간이며,
끝까지 뽑아야 하는 이유가 전역 정렬 요구다.

## 4. 매치 건수에 따른 붕괴

`bench/sql/03_words.sql` 은 주제별 단어에 가중치를 부여하고, 헤더에 예상 등장률까지 적어두었다.
**테니스 주제(topic 21)** 안에 빈도 계층이 그대로 있어서, 주제·문체를 고정한 채 매치 건수만 바꾼 대조군을 만들 수 있다.
(헤더의 예측 "주제 활동어 ≈ 전체의 4.2%" 와 `테니스` 실측 41,679/940,445 = 4.43% 가 일치해 가중치 표는 신뢰할 만하다.)

| 키워드 | weight | 매치 건수 | FT 노드 시간 | 행당 | HTTP (warm 중앙값) |
|---|---|---|---|---|---|
| `리그오브레전드` | — (없는 단어) | **0** | 0.005ms | — | **0.058s** |
| `타이브레이크` | 1 | **99** | 0.80ms | 0.0081ms | **0.102s** |
| `포핸드` | 40 | **3,478** | 21.6ms | 0.0062ms | **0.151s** |
| `복식` | 200 | 미측정 | — | — | **23.3s** |
| `라켓` | 800 | 미측정 | — | — | **30.1s** |
| `테니스` | 3000 | **41,679** | 21,434ms | **0.514ms** | **34.0s** |

읽을 점.

- **매치 건수가 12배(3,478 → 41,679) 늘 때 시간은 992배 뛴다.** 행당 비용 자체가 0.0062ms → 0.514ms 로 **83배** 악화된다.
- **절벽은 weight 40 과 200 사이**에 있다. `포핸드`(3,478건)는 0.15초인데 `복식`(weight 200)은 23.3초다.
  0.15초와 23초 사이에 중간 지대가 사실상 없다.
- 매치가 0건인 키워드는 **0.058초**로 가장 빠르다. 같은 키워드에서 `LIKE` 는 100만 행 풀스캔이었다(5절).
  **두 방식의 최악 케이스가 서로 반대다.**

**행당 비용이 왜 83배나 뛰는지는 규명하지 못했다.** 측정으로 확인한 것은 "매치가 많아지면 건당 비용 자체가 나빠진다"까지이고,
그 메커니즘은 이 문서의 범위 밖이다.

## 5. LIKE 시절과의 비교

전환 전 기록(로컬 bench MySQL 8.4, FULLTEXT·`created_at` 인덱스 **없음**, `LIKE '%keyword%'`):

| 패턴 | 읽은 행 | SQL | API(중앙값) |
|---|---|---|---|
| `테니스` (흔한 키워드) | **337** | 12.2ms | 16.3ms |
| `리그오브레전드` (없는 키워드) | **1,000,000** | 988ms | 877.6ms |
| `테니스` + category | 898 | 1.42ms | 26.8ms |
| `테니스` + category + recruitStatus | 8,984 | 17.5ms | 39.4ms |
| 날짜범위 2023-07 (과거 1개월) | **777,056** | 306ms | 263.6ms |
| 날짜범위 최근 | 12 | 0.29ms | 18.3ms |

**환경이 다르므로 그대로 비교할 수 없다.** 다만 기준점으로 삼을 만한 요청이 하나 있다 — 날짜범위 2023-07 이다.
로컬에서는 PK 를 역순으로 777,056행 훑는 실행 계획이 `EXPLAIN ANALYZE` 로 확인됐다.
**운영에서는 같은 요청의 HTTP 시간만 쟀고 실행 계획은 확인하지 않았다.**

- 로컬 263.6ms vs 운영 6,390ms → **운영이 약 24배 느리다.** 원인은 확인하지 않았다.

이 배수를 그대로 적용하면(단순 환산이며 검증된 보정은 아니다) 키워드 검색 34,000ms 는 로컬 기준 **1,400ms 상당**이 되고,
LIKE 실측 16ms 와는 여전히 약 100배 차이가 남는다.

밀도 계산도 앞뒤가 맞는다. 매치 41,679 / 활성 940,445(로컬 데이터셋 기준) = **4.4%** 이므로 PK 를 역순으로 훑어
11건을 채우는 데 산술적으로 `11 ÷ 0.044 ≈ 250행`이 필요한데, LIKE 실측이 337행이었다.

### 왜 LIKE 가 빨랐나

검색 방식의 우열이 아니라 **정렬 방향과 스캔 방향의 일치 여부**였다.

| | 결과를 내보내는 순서 | `ORDER BY id DESC` | 조기 종료 |
|---|---|---|---|
| LIKE | PK 역순 = `id` 내림차순 | 이미 만족 | **가능** (337행에서 종료) |
| FULLTEXT | `id` 내림차순이 **아님** | 전량 정렬 필요 | **불가** (41,679행 전부) |

LIKE 는 스캔 순서가 곧 정렬 순서라 정렬 비용을 치르지 않았다.
그리고 LIKE 의 약점(없는 키워드 → 100만행 풀스캔 877ms)이 FULLTEXT 의 강점 구간과 겹치므로,
**두 방식의 우열은 키워드 빈도에 따라 뒤집힌다.**

## 6. 데이터셋의 성격

측정 대상은 `bench/sql` 이 생성한 **합성 데이터**다. 본문 단어를 `03_words.sql` 의 가중치 풀에서 뽑아 조립하므로,
키워드별 매치 건수가 그 가중치로 결정된다. `테니스` 의 4.4% 도 실제 글에서 관측된 밀도가 아니라 이 생성 규칙의 결과다.

4절의 대조군이 성립한 것도 같은 이유다 — 가중치를 골라 매치 건수만 바꾼 비교가 가능했다.

**실제 서비스 데이터에서 어떤 키워드가 몇 건에 매치될지는 이 문서에서 알 수 없다.**
따라서 "34초가 실서비스에서도 나타나는가" 는 여기서 답하지 않는다. 열린 항목으로 남긴다.

## 7. 선택지

**아래는 측정 결과가 아니라 앞으로 검토할 후보다. 어느 것도 아직 구현·측정하지 않았다.**

`ORDER BY id DESC` 를 유지하면 FULLTEXT 검색이 매치를 전량 소비한다는 것까지가 측정된 사실이다(2·3절).
그래서 후보는 셋 중 하나를 포기하는 형태가 된다.

| 안 | 포기하는 것 | 근거가 되는 측정 |
|---|---|---|
| A. `ORDER BY id DESC` 를 버린다 | 최신순 정렬 | `ORDER BY` 제거 시 18.2ms (3절) |
| B. LIKE 로 되돌린다 | FULLTEXT | 흔한 키워드 LIKE 16.3ms vs FULLTEXT 34초 (5절) |
| C. 검색엔진을 도입한다 | MySQL 단일 스택 | 없음 |

A 는 정렬 순서가 바뀌므로 `nextCursor` 계약과 프론트가 함께 바뀐다.
B 는 최악 케이스가 반대로 옮겨간다 — LIKE 는 없는 키워드에서 100만 행 풀스캔(로컬 877.6ms), FULLTEXT 는 인기 키워드에서 34초다.

결정은 미결로 둔다.

## 미측정 / 열린 항목

- `복식`(weight 200)·`라켓`(weight 800)의 매치 건수. HTTP 시간만 있고 매치 건수를 재지 않아 절벽 위치를 정확히 못 박았다.
- **매치 건수가 늘 때 행당 비용이 83배 악화되는 원인.** 미규명이다.
  (참고 관측: 같은 키워드라도 첫 실행 2.52초 → 직후 재실행 26ms 로 크게 달라진다.)
- 운영 RDS 데이터가 로컬 bench 데이터셋과 동일한지 미확인. 5절의 밀도 계산은 동일하다는 전제다.
- 깊은 커서 + 키워드 조합 미측정.
- FULLTEXT 가 결과를 **실제로 어떤 순서로 내보내는지** 미확인. `ORDER BY` 없이 반환된 `id` 를 보면 알 수 있다.
- 운영에서 날짜범위 요청의 실행 계획 미확인(HTTP 시간만 측정). 5절의 24배 환산은 이 확인 위에서만 유효하다.
- 실제 서비스 데이터에서 키워드별 매치 건수 분포. 6절의 이유로 이 문서로는 답할 수 없다.
